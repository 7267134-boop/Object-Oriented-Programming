1. נקודת המוצא שלנו: מדוע אנחנו זקוקים למנגנוני הפשטה?

הסכנה הסמויה שמסתתרת אפילו בקטע קוד קצר של 3 שורות

בפרק הקודם אמרתי לך שתכנות מונחה עצמים הוא קודם כל פרדיגמת תכנות שמעניקה לנו מנגנוני הפשטה ייחודיים. אבל לפני שנראה איך נולדו המחלקות והירושה, בוא נשאל את עצמנו שאלה פשוטה: אילו מנגנוני הפשטה אנחנו כבר מכירים משפות תכנות אחרות, ולמה אנחנו בכלל זקוקים להם?

כדי להרגיש את הצורך בהפשטה בידיים, בוא נתבונן במשימה הכי בסיסית שיש: אנחנו רוצים להגדיר מערך בגודל 100 בשפת ++C ולהדפיס את כל איבריו באמצעות לולאת for:

// שלב 1: הקוד הבסיסי ב-++C ללא הפשטה
int a[100];
for (i = 0; i < 100; i++)
    cout << a[i];

על פניו, הקוד הזה עובד. אבל תסתכל טוב על המספר 100: הוא מופיע כאן ישירות פעמיים — פעם אחת בהגדרת גודל המערך (int a[100]), ופעם שנייה בתנאי הסיום של הלולאה (i < 100).

מה הסכנה כאן? נניח שמחר דרישות המערכת משתנות, ואנחנו מתבקשים לעדכן את גודל המערך מ-100 ל-200. בתוכנית אמיתית, הגדרת המערך והלולאה שעוברת עליו עשויות להופיע במרחק של מאות שורות קוד זו מזו (ואולי ישנן 15 לולאות שונות שעוברות על המערך!). קיים חשש ממשי שנעדכן מופע אחד ונשכח לעדכן את המופע השני. חוסר העקביות הזה יוביל לשגיאות ריצה חמורות: או שנתעלם מחצי מהנתונים במערך, או שהלולאה תפלוש לזיכרון שאינו שייך למערך (גלישת חוצץ / Buffer Overflow)! לכן כלל הזהב שלנו הוא: יש להימנע מחזרה על קבועים!

2. מסע ב-6 שלבים: איך מעלים את רמת ההפשטה של המערך והלולאה?

שלב 2 · מאקרו קדם-מעבד #define N 100

הפשטה באמצעות הוראת מאקרו (#define)

כדי לרכז את גודל המערך במקום אחד בלבד, נוכל להשתמש בהוראת קדם-מעבד (Preprocessor):

#define N 100
int a[N];
for (i = 0; i < N; i++)
    cout << a[i];
שלב 3 · מנגנון השפה enum enum {N = 100};

הפשטה באמצעות enum (ויתרונו על פני מאקרו!)

מדוע enum עדיף על מאקרו? כי enum מנוהל ישירות ע"י המהדר (Compiler) של השפה, מכבד את כללי תחום ההכרה (Scope) ומזוהה ע"י מנפה השגיאות (Debugger) — בניגוד למאקרו שמבצע החלפת טקסט עיוורת בקדם-המעבד לפני ההידור!
(החיסרון הקטן מול הקוד הבסיסי: תוספת שורת קוד והגדרת ישות נוספת עבור פעולה פשוטה).

enum {N = 100};
int a[N];
for (i = 0; i < N; i++)
    cout << a[i];
שלב 4 · חישוב אוטומטי ב-++C SIZEOF(array)

מניעת הופעה כפולה של הגודל באמצעות מאקרו SIZEOF

כדי להגדיר את גודל המערך בשורת הגדרת המערך בלבד (ולא להזכיר את הקבוע שוב בלולאה), ניתן לחשב את כמות האיברים דינמית ע"י חלוקת גודל המערך כולו בבתים בגודל איבר בודד:

#define SIZEOF(array) (sizeof(array) / sizeof(array[0]))
int a[100];
for (i = 0; i < SIZEOF(a); i++)
    cout << a[i];
שלבים 5 ו-6 · תמיכה מובנית ב-Java a.length & for-each

המערך כעצם היודע את גודלו (a.length) והפשטת הלולאה (for-each)

ב-Java המערך הוא עצם הנושא את גודלו בשדה מובנה a.length. וברמת ההפשטה הגבוהה ביותר — לולאת for-each מסתירה לחלוטין את ניהול האינדקסים, תנאי הקצה וקידום המונה!

// שלב 5: שימוש בשדה המובנה a.length
int[] a = new int[100];
for (int i = 0; i < a.length; i++) System.out.print(a[i]);
// שלב 6: הפשטת הלולאה כולה (for-each)
for (int k : a) System.out.print(k);

1. מה"תוהו ובוהו" של שפת המכונה אל האסמבלר וייצוג הנתונים (2.2.1–2.2.2)

שמות סימבוליים באסמבלר והפשטה מבוססת נתונים גלובליים ב-Fortran וב-Cobol

החשיבה התכנותית שלנו לא נולדה ביום אחד. בראשית ימי המחשוב, תכנות בשפת מכונה היה בגדר "תוהו ובוהו" — רצפים אינסופיים של מספרים בינאריים או הקסדצימליים וכתובות זיכרון פיזיות מוחלטות. מתוך הצורך האנושי לעשות סדר במורכבות הזו, החלו להתפתח מנגנוני ההפשטה שלב אחר שלב:

2.2.1 · אסמבלר (Assembler) 💻

מעבר ממספרים מוחלטים לשמות סימבוליים

שפת האסמבלר היא אחד ממנגנוני ההפשטה הקדומים ביותר (הנעזר במתרגם/מהדר לתרגום לשפת מכונה). במקום לכתוב קודי פקודות מספריים וכתובות זיכרון מוחלטות, האסמבלר איפשר לייצג כתובות זיכרון באופן סימבולי ולהעניק שמות סימבוליים לאופרטורים ולפקודות הבסיסיות (Mnemonic opcodes).
המגבלה: הקוד באסמבלר עדיין היה בלתי מובנה לחלוטין (Unstructured) וחשוף מאוד לשגיאות.

2.2.2 · ייצוג נתונים (Fortran, Cobol) 🗄️

הפשטה מבוססת נתונים ומידע גלובלי משותף

שפות כגון Fortran ו-Cobol שמו דגש מרכזי על אופן ייצוג הנתונים, ואפשרו הגדרת פעולות ישירות על מבני נתונים (באופן המזכיר עבודה מול מסדי נתונים).
המבנה הארכיטקטוני: קיומו של מאגר נתונים גלובליים (Global Data) משותף במרכז, שמספר פרוצדורות שונות (Proc 1, Proc 2, Proc 3, Proc 4) ניגשות אליו ישירות ומבצעות עליו מניפולציות.

2. פרוצדורות מקוננות (2.2.3), כשל המחסנית הגלובלית והולדת המודול (2.2.4)

איך Pascal קידמה את עקרון הסתרת המידע, איפה היא נכשלה בשיתוף נתונים, ואיך Modula-2 פתרה זאת?

בשלב הבא, שפות כמו Pascal שינו את כיוון החשיבה: במקום לשים את הנתונים הגלובליים במרכז, הן שמו את הדגש על התהליך ועל האלגוריתם המתבצע (פרוצדורות מקוננות – Nested Procedures). בגישה הזו, כל תהליך ראשי (למשל Proc 1) מגדיר באופן לוקלי (מקומי) את מבני הנתונים הדרושים לו (Var 1, Type) ואת תת-התהליכים שלו (Proc 2).

הגישה הזו העניקה למתכנתים קפיצת מדרגה אדירה: יכולת להתרכז ב"מה יש לבצע" במקום ב"איך לבצע", תכנות בשיטת "מהטפחות מטה" (Top-Down Programming), ואת ניצניו הראשונים של עקרון הסתרת המידע (Information Hiding).

אבל אז התגלה פגם חמור במנגנון הסתרת המידע! מה קורה כשאנחנו רוצים לבנות מבנה נתונים כמו מחסנית (Stack) בשפה פרוצדורלית כגון C, כך שמספר פונקציות נפרדות (init, push, top, pop) יפעלו על אותה מחסנית? תסתכל על הקוד הבא:

// משתנים גלובליים חשופים לכל התוכנית!
int datastack[100];
int datatop = 0;

void init() { datatop = 0; }
void push(int val) { if (datatop < 100) datastack[datatop++] = val; }
int top() { if (datatop > 0) return datastack[datatop - 1]; return 0; }
int pop() { if (datatop > 0) return datastack[--datatop]; return 0; }

❌ שתי הבעיות הקשות במימוש המחסנית הגלובלית:

  • פגיעה בהסתרת המידע: כדי שהפונקציות push ו-pop יחלקו את הנתונים, המשתנים datastack ו-datatop חייבים להיות גלובליים! כל חלק אחר בתוכנית יכול לגשת אליהם ישירות ולשבש אותם (למשל לאפס את datatop בטעות).
  • מופע יחיד בלבד: ניתן להחזיק רק מחסנית אחת בכל רגע נתון! מה אם התוכנית זקוקה ל-3 מחסניות שונות במקביל?

📦 2.2.4 הפתרון החלקי: מודול (Module ב-Modula-2)

שפת Modula-2 הוסיפה תמיכה מובנית במודולים: מודול הוא אוסף של פרוצדורות ונתונים עם יכולת שליטה מפורשת על מה שמוחצן החוצה (Export) לעומת הנתונים שנשארים מוסתרים ומוגנים בפנים!
⚠️ המגבלה שעדיין נותרה במודול: מודול מתנהג כמו עצם בודד (Singleton) או כמו מחלקה בעלת מופע יחיד בלבד — עדיין אי אפשר לייצר ממנו ריבוי מופעים עצמאיים באופן טבעי!

1. סעיף 2.2.5: טיפוס נתונים מופשט (Abstract Data Type – ADT)

הפתרון של שפת עדה (Ada) לבעיית המופע היחיד של המודול, וייצוג רשימה באמצעות פירוק למקרים (case)

ראינו קודם שמודול (בשפת Modula-2) פתר את בעיית הסתרת המידע, אבל השאיר אותנו עם מגבלה כבדה: מודול פועל כמו עצם בודד (מופע יחיד). כדי לפתור זאת, שפות כמו Ada (עדה) לקחו את המודולריות צעד מכריע קדימה והוסיפו תמיכה מובנית בטיפוסי נתונים מופשטים (ADT – Abstract Data Type).

מהו ההבדל המהותי בין מודול ל-ADT? ב-ADT המתכנת מגדיר טיפוס חדש לגמרי במערכת! מתוך הטיפוס הזה ניתן ליצור מספר רב של מופעים עצמאיים (Var 1, Var 2, Var 3), כאשר לכל מופע יש מצב פנימי משלו, וכולם חולקים את אותו סט של אופרטורים ופעולות (Op 1, Op 2, Op 3).

בוא נתבונן בדוגמה קלאסית של הגדרת רשימה (List) כטיפוס נתונים מופשט (ADT):

adt List
representation
    list = Nil | CELL of integer * list
operations
    nil = Nil
    cons(x: integer, l: list) = CELL(x, l)
    empty(l: list) = case l of Nil => true | CELL(x, l') => false
    tail(l: list) = case l of Nil => error | CELL(x, l') => l'

שים לב איך פועלים האופרטורים ב-ADT: הפעולות empty(l) ו-tail(l) הן פונקציות שמקבלות את מבנה הנתונים l כפרמטר, ומבצעות עליו פירוק למקרים (case) כדי לשאול מבחוץ: "האם אתה רשימה ריקה Nil או שאתה חוליה CELL?".

2. סעיף 2.2.6: מחלקה (Class) – היפוך המיקוד מפעולות לעצמים!

איך ייצוג מונחה עצמים מעלים את משפטי ה-case, ומה ההבדל בין תכנון מוטה-שורות (ADT) לתכנון מוטה-עמודות (OOP)?

כאן אנחנו מגיעים אל רגע הלידה של תכנות מונחה עצמים (OOP) ואל מושג המחלקה (Class)! בין מושג ה"מחלקה" לבין "טיפוס נתונים מופשט" (ADT) יש דמיון רב: בשפה מונחית עצמים, המחלקה היא אכן טיפוס נתונים מופשט שמאגד נתונים ופעולות ומאפשר ליצור מופעים רבים. אבל יש ביניהם הבדל רעיוני עמוק במיקוד:

  • ב-ADT (טיפוס נתונים מופשט): הדגש מושם על ייצוג הפעולות (האופרטורים) המנתחות את הנתונים.
  • ב-מחלקה (Class ב-OOP): הדגש מושם על ייצוג הנתונים (העצמים) וההתנהגות הפנימית שלהם!

בוא נראה איך נראית אותה רשימה בדיוק כשאנחנו מממשים אותה בגישה מונחית עצמים — על ידי פיצול לשתי ישויות עצמאיות: רשימה ריקה (EmptyList) ורשימה שאינה ריקה (NonEmptyList):

EmptyList = recursive self = record
    empty = true;
    head = error;
    tail = error;
    cons = fun(x) NonEmptyList(x, self);
end
NonEmptyList(x, l) = recursive self = record
    empty = false;
    head = x;
    tail = l;
    cons = fun(x) NonEmptyList(x, self);
end

תסתכל איזה יופי: נעלמו לחלוטין משפטי ה-case! אף פונקציה חיצונית לא צריכה לשאול "איזו רשימה את?". כל עצם (רשימה ריקה או לא-ריקה) "יודע בעצמו" מה להחזיר עבור empty, head ו-tail!

כדי להבין את ההבדל המבני העמוק בין ADT לבין OOP, דמיין טבלה (מטריצה) שבה השורות הן הפעולות (empty?, head, tail) והעמודות הן המבנים/המחלקות (nil, cons):

↔️ הפשטת ADT היא מוטת-שורות (Row-Oriented)

הקוד מאורגן לפי הפעולות (השורות): כל פונקציה (כמו tail) מרכזת בתוכה את הטיפול בכל סוגי המבנים (Nil ו-CELL).
• יתרון: קל להוסיף פעולה חדשה (מוסיפים שורה חדשה).
• חיסרון: הוספת מבנה נתונים חדש מחייבת לפתוח ולעדכן את כל הפונקציות הקיימות!

↕️ הפשטה מונחית עצמים היא מוטת-עמודות (Column-Oriented)

הקוד מאורגן לפי המבנים/המחלקות (העמודות): כל מחלקה (EmptyList או NonEmptyList) מאגדת בתוכה את כל הפעולות עבור עצמה.
• יתרון: קל מאוד להוסיף מחלקה/וריאציה חדשה בלי לגעת בקוד קיים (מוסיפים עמודה חדשה)!
• חיסרון: הוספת פעולה חדשה מחייבת עדכון של כל המחלקות בהיררכיה.

3. סעיף 2.2.7: ירושה (Inheritance) – מ-125,000 שורות קוד ל-10,000 בלבד!

איך מנגנון הירושה מאפשר שיתוף קוד דרמטי בין מחלקות ומונע שכפול מיותר?

השלב השביעי והמכריע בהתפתחות מנגנוני ההפשטה הוא מנגנון הירושה (Inheritance). מהי ירושה? זהו מנגנון הפשטה מתקדם המאפשר שיתוף ושימוש חוזר (Reuse) של קוד והתנהגות בין מחלקות שונות. במקום לכתוב מחדש פעולות דומות בכל מחלקה (כמו cons שראינו קודם שזהה גם ב-EmptyList וגם ב-NonEmptyList), מחלקות יכולות לרשת התנהגות משותפת ממחלקת-על!

כדי להמחיש עד כמה מנגנון הירושה עוצמתי בעולם האמיתי, נערך ניסוי השוואתי מדהים: נלקחה ספרייה תכנותית שלמה שנכתבה בשפת עדה (Ada) (שבה היו טיפוסי נתונים מופשטים ADT אך ללא ירושה מלאה) והכילה 125,000 שורות קוד (125K LOC). אותה ספרייה בדיוק מומשה מחדש בשפת ++C תוך שימוש בעקרונות ה-OOP ובמנגנון הירושה — והתוצאה הייתה מדהימה: המימוש החדש דרש 10,000 שורות קוד בלבד (10K LOC)! צמצום של יותר מ-90% בנפח הקוד בזכות שיתוף קוד בירושה!

שאלה 3 (רמת יישום): השווה בין מימוש הרשימה כ-ADT (Nil | CELL עם case) לבין מימושה המונחה עצמים (EmptyList ו-NonEmptyList). כיצד נעלם משפט ה-case? ▼

💡 ההסבר שלי: במימוש ה-ADT, הפונקציה empty(l) מקבלת רשימה כללית וחייבת לבצע בדיקת תנאי case l of Nil => true | CELL(x, l') => false. במימוש המונחה עצמים פיצלנו את הרשימה לשתי ישויות עצמאיות: EmptyList (שבו קבוע מראש empty = true; head = error; tail = error) ו-NonEmptyList(x, l) (שבו קבוע מראש empty = false; head = x; tail = l). כשאנחנו פונים לעצם ושואלים אותו empty, העצם עצמו כבר יודע מיהו ומחזיר מיד את התשובה הנכונה ללא שום הסתעפות case!

🎯 שורה תחתונה: ב-OOP הידע עובר מהפונקציה החיצונית אל פנים העצם עצמו.
שאלה 4 (רמת ניתוח מבני): הסבר באמצעות מטריצת הפעולות והמבנים מדוע ADT מוגדר כ"מוטה-שורות" ואילו OOP מוגדר כ"מוטה-עמודות", ומהן ההשלכות על הרחבת התוכנה? ▼

💡 ההסבר שלי: במטריצה שבה השורות הן הפעולות (empty?, head, tail) והעמודות הן המבנים (nil, cons):
• ADT הוא מוטה-שורות (Row-Oriented): כל פונקציה מאגדת שורה שלמה (מטפלת בכל המבנים). לכן קל להוסיף פעולה חדשה (שורה חדשה), אך קשה להוסיף מבנה חדש (כי צריך לתקן את ה-case בכל הפונקציות הקיימות).
• OOP הוא מוטה-עמודות (Column-Oriented): כל מחלקה מאגדת עמודה שלמה (כל הפעולות עבור אותו מבנה). לכן קל מאוד להוסיף מחלקה/מבנה חדש (עמודה חדשה ללא נגיעה בקוד קיים), אך קשה יותר להוסיף פעולה חדשה (כי יש להוסיפה לכל המחלקות בהיררכיה).
