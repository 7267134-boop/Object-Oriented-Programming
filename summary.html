1.1 משבר התוכנה, משל הפרחים של באד ושפת Smalltalk הטהורה

💡 מודל מנטלי מנחה – מדוע שפת התכנות מעצבת את החשיבה ההנדסית? לפי תזת צ'רץ'-טיורינג (Church-Turing Thesis), כל חישוב שניתן לביצוע במודל חישובי סביר ניתן למימוש בכל שפת תכנות שלמה-טיורינג (אפילו באסמבלר). אולם לפי היפותזת ספיר-וורף (Sapir-Whorf Hypothesis), הקטגוריות של השפה שבה אנו מדברים ומתכנתים מכתיבות את האופן שבו אנו מפרקים בעיות מורכבות. בעקבות "משבר התוכנה" (Software Crisis) משנות ה-60 וה-70 — שהתבטא בפרויקטי ענק שקרסו בגלל מורכבות בלתי נשלטת (כגון מערכת שינוע המזוודות בשדה התעופה בדנבר, או התרסקות משגר הלוויינים Ariane 5 ב-1996 עקב המרת Float ב-64 סיביות ל-Integer ב-16 סיביות) — נולדה פרדיגמת התכנות מונחה העצמים כדי לנהל מורכבות באמצעות הפשטה, חלוקת אחריות והסתרת מידע.
  • משל משלוח הפרחים של טימותי באד (Budd's Flower Metaphor): כאשר כריס (או סאלי) רוצה לשלוח זר פרחים לרובין בעיר אחרת, הוא אינו שותל זרעים או שוכר משאית בעצמו, אלא פונה לסוכן מתמחה — מוכר הפרחים פרד (או פלורה, מופע של המחלקה Florist היורשת מ-Shopkeeper) ושולח לו הודעה (Message) עם הנתונים הנדרשים (סוג הזר וכתובת היעד). מוכר הפרחים מפעיל שיטה פנימית (Method) ומתקשר עם קהילה שלמה של סוכנים (סיטונאי Wholesaler, מגדל Grower, מעצב זרים FlowerArranger ושליח DeliveryPerson).
    • עקרון הסתרת המידע (Information Hiding / Parnas's Principles): השולח יודע רק "מה" הוא ביקש (החוזה/הפרוטוקול החיצוני), אך אינו יודע ואינו רשאי להתערב ב"איך" המשימה מתבצעת מאחורי הקלעים.
  • ששת עקרונות היסוד של Alan Kay (1993) ושפת Smalltalk כ-Pure OOP: (1) הכל הוא עצם; (2) חישוב מתבצע ע"י תקשורת בין עצמים באמצעות שליחת הודעות; (3) לכל עצם זיכרון פרטי משלו (המורכב גם הוא מעצמים); (4) כל עצם הוא מופע של מחלקה; (5) המחלקה מגדירה את ההתנהגות המשותפת למופעיה; (6) המחלקות מאורגנות בעץ הורשה עם שורש יחיד. בניגוד לשפות היברידיות (כגון Java, C++ ו-C#) המפרידות בין טיפוסים פרימיטיביים (int, boolean) לבין עצמים, שפת Smalltalk (בדומה ל-LISP ול-LOGO) מתבססת על מנגנון הפשטה אחד ויחיד, כמעט נטולת תחביר, ומכריחה לחשוב במונחי עצמים והודעות בלבד. סביבת Squeak היא מימוש קוד-פתוח תואם Smalltalk-80 הכתוב כולו ב-Smalltalk עצמה (Self-Hosting).

1.2 ★ מניעת חזרה על קבועים ו-7 רמות התפתחות מנגנוני ההפשטה

מנגנוני הפשטה בשפות תכנות: משתנים, קבועים, טיפוסי נתונים, פרוצדורות/פונקציות, מודולים, טיפוסי נתונים מופשטים (ADT), מחלקות וירושה. כדי להדגים מדוע הפשטה חיונית למניעת באגים, נבחן סריקת מערך int a[100]; for (i = 0; i < 100; i++) cout << a[i]; ב-5 רמות הפשטה:

שיטת הפשטה קוד מרכזי יתרונות, חסרונות ומלכודות מבחן
1. ללא הפשטה (קבוע כפול) int a[100]; ... i < 100 הסכנה: הקבוע 100 מופיע פעמיים; עדכון גודל המערך ל-200 (או ל-50) ללא עדכון תנאי הלולאה יגרום לסריקה חלקית או לגלישת חוצץ (Buffer Overflow).
2. פקודת מאקרו ב-C++ #define N 100 מגדיר את הגודל במקום אחד, אך מבוצע ע"י הקדם-מעבד (Preprocessor) כהחלפת טקסט עיוורת לפני ההידור, ללא בדיקת טיפוסים, ללא תחום הכרה (Scope) וללא הופעה בטבלת הסימבולים של ה-Debugger.
3. שימוש ב-enum ב-C++ enum {N = 100}; int a[N]; יתרון לעומת מאקרו: enum הוא חלק משפת התכנות עצמה ומטופל ע"י המהדר (כפוף ל-Scope ולבדיקות טיפוסים).
חיסרון לעומת קבוע ישיר: דורש שורת קוד נוספת ומפצל את הגדרת המערך וגודלו לשתי שורות נפרדות.
4. מאקרו חישוב גודל #define SIZEOF(arr) (sizeof(arr)/sizeof(arr[0])) משלב את שני היתרונות: הגדרה בשורה אחת (int a[100];) והימנעות מכפילות הקבוע. מלכודת C/C++: נכשל כאשר המערך מועבר כפרמטר לפונקציה כי אז הוא דועך למצביע (Array Decay)!
5. תמיכה מובנית ב-Java / OOP a.length או for (int k : a) המערך הוא עצם היודע בעצמו את אורכו (a.length ב-Java, או a size ב-Smalltalk), ובלולאת for-each (או a do: [:k | ...]) מופשט גם מנגנון האינדקס!
שבע תחנות התפתחות מנגנוני ההפשטה והיפוך המטריצה בין ADT (מוטה-פעולות) ל-OOP (מוטה-עצמים)
1. אסמבלר (Assembler): שמות סימבוליים לכתובות ולאופרטורים במקום מספרים בינאריים, אך הקוד שטוח ואינו מובנה.
2. הפשטה מבוססת נתונים (Fortran, Cobol): דגש בייצוג מבנה הנתונים הגלובלי (Global Data) ופרוצדורות חיצוניות הפועלות עליו. החיסרון: כל פרוצדורה חשופה למבנה הנתונים ועלולה להשחיתו.
3. הפשטה מבוססת תהליכים / פרוצדורות מקוננות (Pascal, C): פירוק פונקציונלי מלמעלה למטה (Top-Down). החיסרון (במחסנית ב-C): כדי לשתף את המחסנית בין init(), push(val), top() ו-pop(), חייבים לחשוף משתנים גלובליים (int datastack[100]; int datatop = 0;).
4. מודול (Modula-2): אוסף פרוצדורות ונתונים עם הפרדה בין מנשק מוחצן (Export) למימוש מוסתר. המגבלה הקריטית: מודול הוא כמו עצם בודד או מחלקה עם מופע יחיד בלבד (אי אפשר ליצור שתי מחסניות עצמאיות באותה תוכנית!).
5. טיפוס נתונים מופשט (ADT ב-Ada): מאפשר להגדיר טיפוס חדש שייתכנו ממנו כמה מופעים שלכל אחד סט אופרטורים משלו. בהגדרת adt List עם list = Nil | CELL of integer * list, הדגש הוא בייצוג הפעולות (מוטה-שורות): כל פעולה כגון empty(l) או tail(l) חייבת לבצע פיצול מקרים מפורש (case l of Nil => ... | CELL(x, l') => ...).
6. מחלקה (Class ב-OOP): טיפוס נתונים מופשט שבו הדגש מושם בייצוג הנתונים (העצמים) במקום בייצוג הפעולות! (מוטה-עמודות): מגדירים את EmptyList (שבה empty = true; head = error; tail = error; cons(x) = NonEmptyList(x, self)) ואת NonEmptyList(x, l) (שבה empty = false; head = x; tail = l; cons(y) = NonEmptyList(y, self)) תוך שימוש בהתייחסות עצמית (recursive self). הוספת וריאנט חדש של רשימה ב-OOP דורשת הוספת מחלקה חדשה בלבד בלי לשנות אף שורת קוד קיימת!
7. ירושה (Inheritance) ו-4 רמות ההפשטה ב-OOP: ירושה מאפשרת שיתוף קוד בין מחלקות ביחס "is-a" (ספרייה בת 125K שורות קוד ב-Ada צומצמה ל-10K שורות בלבד ב-C++ בעזרת ירושה!), לצד יחס הרכבה "has-a" (Composition). בנוסף, ארכיטקטורת OOP פועלת ב-4 רמות הפשטה: (1) רמת הקהילה (עצמים המתקשרים להשגת מטרה), (2) רמת היחידה (Package / Namespace), (3) רמת המנשק ("מה" העצם עושה כלפי חוץ), ו-(4) רמת המימוש ("איך" העצם מממש זאת בפנים).

1.3 ★ המושג "עצם", מרחב הבעיה מול הפתרון ושלושת מאפייני העצם

  • עצם מול מחלקה – איזה מושג בסיסי יותר ואיזה חשוב יותר? המושג "עצם" (Object) הוא בסיסי יותר (הישות הקונקרטית הקיימת בזמן ריצה), אך למעשה מושג ה"מחלקה" (Class) הוא חשוב יותר בהנדסת תוכנה משום שהוא מנגנון ההפשטה המגדיר קבוצות אינסופיות של עצמים בעלי מבנה והתנהגות משותפים.
  • סיווג עצמים למרחב הבעיה (`Problem Space`) ולמרחב הפתרון (`Program / Solution Space`):
    • עצמים ממרחב הבעיה: מייצגים ישויות מעולם הלקוח והמציאות, כגון עובד, שעון נוכחות, פריט במלאי, פטיש בחנות, מספר מרוכב $e+2i$, כלי רכב נושא לוחית זיהוי 19-070-35, או רשימה ממרחב הבעיה (כגון רשימת קניות או רשימת נוכחות תלמידים).
    • עצמים ממרחב התכנית/הפתרון: מייצגים מבני עזר תכנותיים של המפתח, כגון קובץ מערכת (FILE*), מחסנית זיכרון, טבלת גיבוב, או רשימה ממרחב הפתרון (כגון רשימת בלוקים פנויים במנהל הזיכרון). רשימה כגון (13, "hello", true) היא דואלית ויכולה להשתייך לכל אחד משני המרחבים לפי הקשר השימוש בה.

🔨 שלושת מאפייני העצם ($\text{Object} = \text{Identity} + \text{State} + \text{Behavior}$) וארבע הדוגמאות:

1. זהות (Identity) תכונה המבדילה את העצם מכל שאר העצמים (לרוב כתובת הזיכרון שבה הוא שמור). מאפשרת לקבוע אם שני שמות מתייחסים לאותו עצם ממש. זהות העצם צמודה לחייו ואינה משתנה לעולם!
2. מצב (State – המאפיין הסטטי) אוסף הערכים הנוכחיים בתכונות העצם. יכול להשתנות לאורך חיי העצם (אלא אם העצם הוא נצחי / Immutable כגון מספר מרוכב או נקודה קבועה).
3. התנהגות (Behavior – המאפיין הדינמי) אוסף הפעולות שהעצם מבצע בתגובה להודעות שהוא מקבל מלקוחותיו.
4 הדוגמאות הקלאסיות: (1) פטיש בחנות: זהות = הפטיש הספציפי שנבחר מבין הפטישים על המדף; מצב = מוצג למכירה; התנהגות = נעיצת מסמרים. (2) המספר המרוכב $e+2i$: זהות = מופע המספר; מצב = חלק ממשי $e$, חלק מדומה $2$ וערך מוחלט (עצם נצחי!); התנהגות = חיבור, חיסור, כפל וחילוק. (3) הרשימה (13, 'hello', true): זהות = מופע הרשימה; מצב = האיברים ואורך הרשימה; התנהגות = הוספת/מחיקת איבר, הדפסה, מעבר על האיברים ומיון. (4) כלי רכב 19-070-35: זהות = הרכב עצמו (שימו לב: לוחית הזיהוי היא תכונה במצב הרכב, בעוד הזהות היא ישות הרכב הפיזית!); מצב = מהירות, מיקום, צבע; התנהגות = נסיעה, האצה, האטה ועצירה.

♻️ מחזור חיי עצם (Object Lifetime) ושלושת אלגוריתמי איסוף הזבל (Garbage Collection):

יצירה ואתחול: בפקודה a := Animal new, המחלקה היא זו שמייצרת את העצם (מקצה זיכרון ומחזירה את מזהה העצם), ואילו העצם עצמו הוא זה שמבצע את אתחול ערכיו (באמצעות מתודת המופע initialize!). לעומת זאת, בהשמת ליטרל a := 4, המספר 4 הוא עצם קיים מסוג SmallInteger המוצב ישירות במשתנה.
זמן חיים: עצם יכול לחיות כל זמן שהתוכנית רצה (עצם גלובלי כגון Transcript), בזמן ריצת בלוק/פונקציה (על המחסנית ב-C++), מיצירה ועד שחרור ידני (delete ב-C++), או מיצירה ועד שאין אליו עוד התייחסויות בשפות עם איסוף זבל אוטומטי (Garbage Collection) כגון Smalltalk, Java ו-C#:

1. ספירת מצביעים (Reference Counting – Collins 1960): לכל עצם שדה מונה RC (מאותחל ל-1 ביצירה). בכל השמת מצביע, העצם החדש מקבל RC++ והקודם RC--. כש-RC == 0 העצם נמחק ומפחית רקורסיבית 1 מכל העצמים שעליהם הצביע. חיסרון: אינו משחרר מעגלי מצביעים!
2. סימון וטאטוא (Mark and Sweep – McCarthy 1960): פועל ב-2 שלבים כשהזיכרון מתמלא: שלב הסימון (Mark) עובר מכל משתני השורש ומסמן כל עצם נגיש; שלב הטאטוא (Sweep) סורק את כל ה-Heap ומוחק כל עצם שאינו מסומן (פותר מעגלים!).
3. עצירה והעתקה (Stop and Copy): מחלק את ה-Heap לשני חצאים (חצי פעיל וחצי פנוי). כשהחצי הפעיל מתמלא, מעתיקים ברצף רק את העצמים החיים הנגישים אל החצי השני (מה שמונע פרגמנטציה!) ומחליפים תפקידים בין שני החצאים.

1.5 ★ זהות מול שוויון (== / =), העתקות (רדודה/עמוקה/רקורסיבית) ו-6 סוגי המתודות

  • שם מול זהות והמזהה השמור לעצם הנוכחי: ייתכנו שני עצמים בעלי אותו שם (בתחומי הכרה שונים), עצם בעל כמה שמות (Aliasing), או עצם אנונימי ללא שם כלל — אך לעולם לא ייתכנו שני עצמים בעלי אותה זהות. המזהה השמור לעצם הנוכחי: ב-Smalltalk: self | ב-Java וב-C++: this | ב-Eiffel: Current.
  • השוואת זהות (`==`) מול השוואה מבנית (`=`) וחוזה ה-`hash`:
    • השוואת הזהות (==, ושלילתה ~~): מחזירה true אמ"ם שני השמות מצביעים לאותו עצם ממש בזיכרון.
    • השוואה מבנית (=, ושלילתה ~=): בודקת אם לשני העצמים יש מבנה ומצב שווים (למשל עבור a := 5 + 3. b := 8.0 מתקיים a = b → true, אך a == b → false!). ב-Object ברירת המחדל של = היא ^ self == anObject. כאשר דורסים את = במחלקה, חובה לדרוס בהתאמה גם את hash כך שלכל a = b יתקיים בהכרח a hash = b hash!

📋 סיווג סוגי העתקת עצמים (על רשימת נקודות class PList { public Point head; public PList tail; }):

  • 1. העתקה זהותית (`b := a`): המצביע לעצם משוכפל בלבד; בסיום יש שני שמות לאותו עצם ממש ונותרת זהות אחת בלבד (a == b).
  • 2. העתקה מבנית (יוצרת עצם חדש בעל זהות חדשה):
    • העתקה רדודה (`oneLevelCopy` / `shallowCopy`): השורש מועתק מבנית (PList res = new PList();), אך העצמים הפנימיים מועתקים זהותית (res.head = head; res.tail = tail;).
    • העתקה רדודה לעומק 2 (`twoLevelCopy` / `copyTwoLevel`): משכפלת את השורש ואת הרמה הראשונה של העצמים הפנימיים (res.head = new Point(head.x, head.y); if (tail != null) res.tail = tail.oneLevelCopy();), אך מרמה 3 ומטה המצביעים נותרים משותפים.
    • העתקה עמוקה (`deepCopy`): משכפלת מבנית את השורש ואת כל חוליות הזנב והנקודות הפנימיות לכל עומק העץ. מלכודת מבחן: במבנה נתונים עם הצבעה מעגלית, deepCopy תיכנס לרקורסיה אינסופית!
    • העתקה רקורסיבית (`copy` הקוראת ל-`head.copy()` ול-`tail.copy()`): עומק ההעתקה נקבע ע"י העצמים הפנימיים! כאשר המחלקה Point מוגדרת עם שדות קבועים public final int x, y; (כלומר Point היא עצם נצחי / Immutable שמצבו אינו יכול להשתנות לעולם), Point.copy() יכולה לבצע return this; (העתקה זהותית של הנקודה מבלי לשכפל אותה לשווא בזיכרון), בעוד חוליות ה-PList משוכפלות מבנית לכל אורך הרשימה! ב-Smalltalk המתודה Object>>copy קוראת ל-self shallowCopy postCopy, ותתי-מחלקות דורסות את postCopy לשכפול רכיביהן הפנימיים.
🧱 מאפיינים סטטיים ודינמיים של עצמים: • סטטיים: תכונה (attribute / field / property / instance variable / data member – המקום שבו נשמר המצב), מבנה (structure – אוסף התכונות), מצב (state – אוסף הערכים במבנה), ועצם נצחי (Immutable – מורכב מתכונות נצחיות בלבד).
• דינמיים: עצם אקטיבי (יוזם פעולות בעצמו, כמו Task ב-Ada) מול עצם פסיבי (פועל רק בקבלת הודעה); הודעה (Message – הבקשה הסימבולית ששולח הלקוח), שיטה/מתודה (Method – הקוד שהעצם בורר ומריץ), ופרוטוקול (Protocol – אוסף ההודעות שהעצם מבין).
🛠️ ששת סוגי הפעולות (המתודות) בממשק העצם: 1. Constructor (בנאי): יצירת העצם ואתחול מצבו הראשוני.

  • כרטיסי CRC (Class-Responsibility-Collaborators): כרטיס תכנון לכל מחלקה המפרט: (1) שם המחלקה, (2) תחומי האחריות שלה (Responsibilities), ו-(3) השותפים שלה (Collaborators) – המחלקות האחרות שאיתן היא מתקשרת להשלמת אחריותה. המגבלה הפיזית של גודל הכרטיס מונעת יצירת "מחלקת-אל" עמוסה מדי!
  • תאחיזה גבוהה (High Cohesion) וצימוד נמוך (Low Coupling): שואפים לתאחיזה גבוהה (כל הפעולות במחלקה קשורות באופן הדוק לאחריות אחת בהירה) ולצימוד נמוך (צמצום התלות של מחלקה אחת במבנה הפנימי של מחלקות אחרות, כדי ששינוי עתידי ישפיע על מינימום רכיבים).

3.2 ★ שלושת סוגי ההודעות, חוקי הקדימויות וחוק הרצף הארוך ביותר

סדר הקדימויות המחמיר ב-Smalltalk: סוגריים () → אונרי (Unary) → בינארי (Binary) → מילות-מפתח (Keyword)
דוגמאות חישוב קדימויות למבחן:
• 2 raisedTo: 1 + 3 factorial $\implies$ קודם אונרי 3 factorial (=6), אז בינארי 1 + 6 (=7), ולבסוף מילת-מפתח 2 raisedTo: 7 = 128!
• 2 * 3 factorial raisedTo: 2 $\implies$ קודם אונרי 3 factorial (=6), אז בינארי 2 * 6 (=12), ולבסוף מילת-מפתח 12 raisedTo: 2 = 144!
• a := 0. a + (a := 3) $\implies$ ב-Smalltalk המקבל a משוערך קודם (לערך 0), לאחר מכן הארגומנט (a := 3) משוערך ל-3, ולכן 0 + 3 מחזיר 3! לעומת זאת a := 0. (a := 3) + a משערך קודם את המקבל ל-3 (ומעדכן את a ל-3) ואז מחבר 3 + 3 ומחזיר 6!
⚠️ חוק הרצף הארוך ביותר במילות-מפתח (Longest Keyword Match) ומלכודת חוסר סוגריים: המפענח של Smalltalk מאחד את כל מילות-המפתח הרצופות באותה רמת סוגריים לבורר (Selector) אחד ארוך:
• בביטוי st := 'hello'. st at: (st indexOf: $e) put: $x הסוגריים הכרחיים (מחזיר $x והמחרוזת הופכת ל-'hxllo'); ללא הסוגריים המערכת מחפשת מתודה אחת בשם at:indexOf:put: וזורקת MessageNotUnderstood!
• מלכודת מבחן קלאסית: הביטוי a > 5 and: [a < 10] ifTrue: [Transcript show: 'ok'] (ללא סוגריים סביב תנאי ה-and:!) מאחד את מילות המפתח and: ו-ifTrue: להודעה אחת בשם and:ifTrue: הנשלחת לתוצאת a > 5, וזורק MessageNotUnderstood: True>>and:ifTrue:! תיקון: (a > 5 and: [a < 10]) ifTrue: [...].

3.3 ★ סדרת ביטויים (.) מול מפל הודעות Cascade (;) ומלכודת yourself

🌊 כללי הזהב של מפל הודעות Cascade (`;`): התו ; שולח רצף הודעות אל אותו עצם מקבל בדיוק — המקבל של ההודעה הראשונה שלפני ה-; הראשון, ומחזיר כערך את תוצאת ההודעה האחרונה ברצף:
  • 3 + 4; + 5 $\implies$ המקבל של + 4 הוא 3, ולכן גם + 5 נשלחת ל-3 $\implies$ מחזיר 8!
  • 2 raisedTo: 2; * 3 factorial $\implies$ המקבל של raisedTo: 2 הוא 2; בהודעה השנייה קודם מחושב הארגומנט האונרי 3 factorial (=6) ואז ההודעה הבינארית * 6 נשלחת למקבל המקורי 2 $\implies$ מחזיר 12!
  • 10@10 - 10; corner: 30@30; isZero $\implies$ ההודעה הראשונה לפני ה-; היא - 10 שהמקבל שלה הוא הנקודה 10@10; לכן בסוף (10@10) isZero מחזיר false! לעומת זאת, ללא ה-; הראשונה: 10@10 - 10 corner: 30@30; isZero $\implies$ ההודעה שלפני ה-; היא corner: 30@30 שהמקבל שלה הוא תוצאת 10@10 - 10 כלומר הנקודה 0@0, ולכן (0@0) isZero מחזיר true!
  • (10@10 + 20; corner: 30@30) area $\implies$ המקבל הוא 10@10, נוצר מלבן מ-10@10 עד 30@30 ששטחו 400. ללא ה-;: (10@10 + 20 corner: 30@30) area יוצר מלבן מ-30@30 עד 30@30 ששטחו 0!
  • מלכודת `add:` ו-`yourself`: המתודה add: anObject באוספים מחזירה את האיבר שהוסף (anObject) ולא את האוסף! לכן c := OrderedCollection new add: 1; add: 2 יציב ב-c את המספר 2! כדי לקבל את האוסף עצמו חובה לסיים ב-; yourself (המוגדרת ב-Object>>yourself ^ self).

4.1 מבנה המתודה ב-Smalltalk, איסור השמה לפרמטר ופרימיטיבים

📝 4 מרכיבי המתודה ודוגמת `LinkedList>>add:after:`: (1) כותרת/תבנית המתודה (Method Pattern), (2) הערת תיעוד במירכאות כפולות "...", (3) הצהרת משתנים מקומיים זמניים | savedLink | (מאותחלים ל-nil), ו-(4) גוף המתודה.
• איסור השמה לפרמטר (חוק קומפילציה במבחנים!): פרמטרים של מתודה הם לקריאה בלבד! ניסיון לבצע השמה aParam := 5 בתוך מתודה גורם לשגיאת הידור (Syntax/Compilation Error)!

LinkedList >> add: link after: otherLink
    | savedLink |
    lastLink == otherLink ifTrue: [^ self addLast: link].
    savedLink := otherLink nextLink.
    otherLink nextLink: link.

4.2 ★ בלוקים (BlockClosure), סגורים לקסיקליים ויציאה לא-מקומית (^)

  • בלוקים כעצמים ממדרגה ראשונה (`BlockClosure` / `BlockContext`): בלוק [ :x :y | | localTemp | ... ] דוחה את הערכת הביטויים שבתוכו עד לשליחת הודעת הפעלה: value (ללא פרמטרים), value: (פרמטר 1), value:value: (2 פרמטרים, עד 4), או valueWithArguments: anArray. הערך המוחזר מהבלוק הוא ערך הביטוי האחרון שבו (בלוק ריק [] value מחזיר nil).
  • סגור לקסיקלי (Lexical Closure): בלוק לוכד ושומר הפניה לסביבה הלקסיקלית (המשתנים המקומיים ומשתני המופע של מתודת הבית) שבה הוגדר, גם כאשר הוא מועבר כארגומנט או מוחזר מן המתודה ומורץ מאוחר יותר במקום אחר! לדוגמה, במתודה b | i | i := 5. ^ [i := i + 1], כל שליחה של value לבלוק המוחזר תקדם את אותו משתנה לכוד i (תחזיר 6, אחר כך 7 וכן הלאה).

🚀 שאלת המבחן הקלאסית: יציאה לא-מקומית מתוך בלוק (`Non-Local Return` – האופרטור `^`):

ב-Smalltalk, האופרטור ^ בתוך בלוק אינו יוצא רק מהבלוק, אלא יוצא מיד ממתודת הבית (Home Method) שבתוכה נכתב הבלוק לקסיקלית, תוך קיפול כל מסגרות המחסנית הביניים! לעומת זאת, סיום בלוק ללא ^ מחזיר את הערך רק למי ששלח לבלוק את ההודעה value. 

// מעקב הבחינה הקלאסי (מה ידפיס ויחזיר Exam new a?):
Exam >> a
    Transcript show: 'Start a'; cr.
    self b.
    Transcript show: 'End a'; cr.

Exam >> b
    Transcript show: 'Start b'; cr.
    self c: [ Transcript show: 'Inside block'; cr. ^ 'Return from b!' ].
    Transcript show: 'End b'; cr.

Exam >> c: aBlock
    Transcript show: 'Start c'; cr.
    aBlock value.
    Transcript show: 'End c'; cr.

// 1. מדפיס: Start a -> קורא ל-self b -> מדפיס: Start b -> קורא ל-self c: [...] -> מדפיס: Start c.
// 2. ב-c: מופעל aBlock value -> מדפיס: Inside block.
// 3. הפקודה ^ 'Return from b!' נמצאת בתוך בלוק שהוגדר לקסיקלית במתודה b! לכן היא פולטת ומסיימת מיד גם את c: וגם את b!
// 4. 'End c' ו-'End b' לא יודפסו לעולם! הבקרה חוזרת ל-a אחרי השורה self b, ומדפיסה: End a!

4.3 ★ בוליאניים פולימורפיים (True/False, and: מול &), לולאות ו-SUnit

🔀 מימוש פולימורפי של `Boolean` (`True` ו-`False`): ב-Smalltalk אין מילת מפתח if! המחלקה המופשטת Boolean מורישה לשתי תתי-מחלקות קונקרטיות יחידניות: True (מופע יחיד true) ו-False (מופע יחיד false) המממשות הפוך את ifTrue:ifFalse:: 
True >> ifTrue: trueBlock ifFalse: falseBlock
    ^ trueBlock value
False >> ifTrue: trueBlock ifFalse: falseBlock
    ^ falseBlock value
// שימו לב: false ifTrue: [...] מחזיר nil!
מלכודת מבחן קריטית (`and:` / `or:` מול `&` / `|`):
• and: aBlock ו-or: aBlock (חישוב מקוצר / Short-Circuit): מקבלות בלוק [...]! ב-False>>and: alternativeBlock ^ self הבלוק אינו מוערך כלל (וב-True>>and: alternativeBlock ^ alternativeBlock value).
• & aBoolean ו-| aBoolean (חישוב מיידי / Eager): הן הודעות בינאריות המקבלות ערך בוליאני מוכן (ולא בלוק!), ומשערכות תמיד את שני האגפים לפני שליחת ההודעה! לכן שליחת בלוק true & [false] ב-True>>& aBoolean ^ aBoolean תחזיר את עצם הבלוק [false] במקום false!
🔁 מימוש הלולאות ובדיקות יחידה ב-`SUnit`: 
// 1. לולאת whileTrue: על בלוק תנאי (BlockClosure):

  • 5 קטגוריות המימוש של אוספים בזיכרון: (1) מימושי מערך (`Array`): האיברים שמורים במשתנים מאונדקסים של האוסף עצמו ולכן גודלו קבוע; (2) מימושים סדורים (`OrderedCollection, SortedCollection`): מחזיקים מערך פנימי במשתנה מופע array עם שני מצביעי גבולות firstIndex ו-lastIndex, וכשהוא מתמלא מקצים מערך חדש גדול יותר; (3) מימושי גיבוב (`Set, Dictionary` ו-`Bag`): טבלת גיבוב; Bag ממומש בפנים ע"י Dictionary שבו כל איבר הוא המפתח ומספר המופעים (occurrencesOf:) הוא הערך; (4) מימושים מקושרים (`LinkedList`): שרשרת חוליות שיורשות מ-Link; (5) מימוש אינטרוול (`Interval`): שומר 3 מספרי start, stop, step בלבד ללא אחסון האיברים בזיכרון!
מחלקת אוסף סדור / גישה דינמי (Growable)? כפילויות? דרכי יצירה, מתודות והבחנות מבחן (Set/Bag מול IdentitySet/IdentityBag)
Array אינדקס 1..n לא (גודל קבוע) כן (הטרוגני) Array new: 5 (מאותחל ל-5 איברי nil), #(...), {...}. תומך ב-at: ו-at:put: אך זורק `shouldNotImplement` על `add:` ו-`remove:`!
OrderedCollection לפי סדר הכנסה כן כן add: (מוסיף בסוף), addFirst:, addLast:, at:, at:put:, remove: (מסיר את המופע הראשון השווה לארגומנט).

Dictionary / IdentityDictionary לפי מפתח (Keyed) כן (Hash) מפתחות ייחודיים זוגות Association (#one->1). keys מחזיר Set, values מחזיר Array, ו-do: על מילון סורקת את ה-ערכים (`values`)!

    newCollection := self species new.
    self do: [:each | newCollection add: (aBlock value: each)].
    ^ newCollection
// זהירות במבחן: collect: על String יוצרת String חדש ולכן הבלוק חייב להחזיר תווים (Character)!

Collection >> select: aBlock
    | newCollection |
    newCollection := self species new.
    self do: [:each | (aBlock value: each) ifTrue: [newCollection add: each]].
    ^ newCollection

Collection >> reject: aBlock
    ^ self select: [:element | (aBlock value: element) == false]

Collection >> detect: aBlock ifNone: exceptionBlock
    self do: [:each | (aBlock value: each) ifTrue: [^ each]].   "יציאה לא-מקומית ^ ברגע שנמצא הראשון!"
    ^ exceptionBlock value

Collection >> inject: thisValue into: binaryBlock
    | nextValue |
    nextValue := thisValue.
    self do: [:each | nextValue := binaryBlock value: nextValue value: each].
    ^ nextValue

7.1 ★ סימולציה מבוזרת ב-OOP, ייצוג תמורה, 4 אופני הייצוג ו-8 סימטריות הלוח

  • הגדרת חידת 8 המלכות והפרדיגמה המבוזרת: הצב 8 מלכות על לוח שחמט $8 \times 8$ כך שאף מלכה אינה מאיימת על מלכה אחרת (אין שתי מלכות באותה שורה, באותה עמודה או באותו אלכסון). בגישה פרוצדורלית מנהל מרכזי מזיז נתונים פסיביים במערך גלובלי באמצעות לולאות מקוננות; בגישה מונחית עצמים מבוזרת אין מנהל מרכזי ואין מערך גלובלי — כל מלכה היא סוכן אוטונומי האחראי לעמודה שלה ומנהל משא ומתן אך ורק עם שכנתו משמאל (neighbor)!
    • ייצוג פתרון כתמורה (Permutation): מכיוון שבכל עמודה ובכל שורה יש בדיוק מלכה אחת, ניתן לייצג כל פתרון כתמורה מעל $\{0, 1, \dots, 7\}$, למשל: $$\begin{pmatrix} 0 & 1 & 2 & 3 & 4 & 5 & 6 & 7 \\ 7 & 3 & 0 & 2 & 5 & 1 & 6 & 4 \end{pmatrix}$$
1. ייצוג אלגברי (זוגות סדורים) עבור $A = \{0, \dots, N-1\}$ ו-$B = A \times A$, תת-קבוצה $C \subseteq B$ בגודל $N$ היא פתרון אם לכל שתי מלכות שונות $Q_k(i_k, j_k), Q_l(i_l, j_l) \in C$ מתקיימים 4 התנאים:
1. עמודה: $i_k \ne i_l$  |  2. שורה: $j_k \ne j_l$
3. אלכסון ראשי: $i_k + j_k \ne i_l + j_l$  |  4. אלכסון משני: $i_k - j_k \ne i_l - j_l$
2. ייצוג בחשבון מודולרי ($0 \dots N^2-1$) לכל $x \ne y \in B \subseteq \{0, \dots, N^2-1\}$ בגודל $N$:
1. עמודה: $x \not\equiv y \pmod N$  |  2. שורה: $\lfloor x/N \rfloor \ne \lfloor y/N \rfloor$
3. אלכסון: $(x \bmod N) + \lfloor x/N \rfloor \ne (y \bmod N) + \lfloor y/N \rfloor$
4. אלכסון נגדי: $(x \bmod N) - \lfloor x/N \rfloor \ne (y \bmod N) - \lfloor y/N \rfloor$
3. קבוצה יציבה מקסימלית (Maximum Stable Set) בגרף האיומים $G=(V,E)$ שבו $|V|=N^2$ ויש קשת ב-$E$ בין כל שתי משבצות שמאיימות זו על זו, פתרון הוא תת-קבוצת צמתים יציבה $V' \subseteq V$ בגודל $N$ שאין בה אף קשת.
4. קליק מקסימלי (Maximum Clique) בגרף המשלים (גרף אי-האיום) שבו יש קשת ב-$E$ בין כל שתי משבצות שאינן מאיימות זו על זו, פתרון הוא קליק $V' \subseteq V$ בגודל $N$ שבו בין כל שני צמתים יש קשת ($\binom{N}{2}$ קשתות).

* 8 סימטריות הלוח ופתרונות זרים ממש: תחת 4 סיבובים דו-ממדיים ($90^\circ, 180^\circ, 270^\circ, 360^\circ$) ו-4 שיקופים תלת-ממדיים במרחב (סביב הציר האופקי, האנכי ושני האלכסונים), מתקבלים בלוח $8 \times 8$ סה"כ 92 פתרונות, מתוכם 12 פתרונות זרים ממש (עצמאיים). (עבור $N=1..8$ סך הפתרונות: $1, 0, 0, 2, 10, 4, 40, 92$; פתרונות זרים: $1, 0, 0, 1, 2, 1, 6, 12$).

7.2 ★ הפתרון המבוזר המלא ב-Smalltalk: המחלקות Board, Queen ו-QueenTerminator

ארכיטקטורת הרשימה המקושרת בפתרון המבוזר של 8 המלכות: כל מלכה מכירה רק את שכנתה משמאל (neighbor)
// ================= 1. המחלקה Board =================
Object subclass: #Board
    instanceVariableNames: 'lastQueen'
    classVariableNames: '' poolDictionaries: '' category: 'OOD-8Queens'

Board >> initialize
    lastQueen := QueenTerminator new.
    (1 to: 8) do: [:i |
        lastQueen := Queen new setColumn: i neighbor: lastQueen]

Board >> solve
    Transcript clear.
    lastQueen firstSolution
        ifTrue: [
            Transcript show: lastQueen result printString; cr.
            [lastQueen nextSolution] whileTrue: [
                Transcript show: lastQueen result printString; cr].
            Transcript show: 'End of Solutions.'; cr]
        ifFalse: [Transcript show: 'No Solution.'; cr]

// ================= 2. המחלקה Queen (3 משתני מופע ו-7 מתודות) =================
Object subclass: #Queen
    instanceVariableNames: 'row column neighbor'
    classVariableNames: '' poolDictionaries: '' category: 'OOD-8Queens'

Queen >> setColumn: aColumn neighbor: aQueen
    column := aColumn. neighbor := aQueen

Queen >> firstSolution
    neighbor firstSolution.
    row := 1.
    ^ self moveToNextNonAttackedRow

Queen >> nextSolution
    ^ self advance and: [self moveToNextNonAttackedRow]

Queen >> result
    ^ neighbor result addLast: row; yourself   "חובה ; yourself כי addLast: מחזירה את row!"

Queen >> advance
    row = 8 ifTrue: [
        neighbor nextSolution ifFalse: [^ false].
        row := 0].
    row := row + 1.
    ^ true

Queen >> moveToNextNonAttackedRow
    [neighbor canAttack: row x: column]
        whileTrue: [self advance ifFalse: [^ false]].
    ^ true

Queen >> canAttack: testRow x: testColumn
    | columnDifference |
    columnDifference := testColumn - column.
    ((row = testRow
        or: [row + columnDifference = testRow])
        or: [row - columnDifference = testRow])
            ifTrue: [^ true].
    ^ neighbor canAttack: testRow x: testColumn

// ================= 3. המחלקה QueenTerminator (תבנית Null Object) =================
Object subclass: #QueenTerminator
    instanceVariableNames: '' classVariableNames: '' poolDictionaries: '' category: 'OOD-8Queens'

QueenTerminator >> canAttack: testRow x: testColumn  ^ false
QueenTerminator >> firstSolution                     ^ true
QueenTerminator >> nextSolution                      ^ false
QueenTerminator >> result                            ^ OrderedCollection new

7.3 ★ מלכודת משתנה המחלקה N, לוח תלת-ממדי N×N×N ווריאציות המבחנים

🚨 מלכודת משתנה המחלקה N בהכללת הלוח ל-$N \times N$ (שאלת בחינה קלאסית!):

אם נגדיר ב-Board משתנה מחלקה משותף classVariableNames: 'N' ומתודת מחלקה Board class>>N ^ N, וב-Queen>>advance נבדוק row = Board N, אזי בהרצת:
board1 := Board new initialize: 5. board2 := Board new initialize: 1. board1 solve.
הקריאה board2 initialize: 1 דורסת את משתנה המחלקה המשותף N ל-1 עבור כל מופעי הלוחות במערכת! לכן 5 המלכות של board1 לא יתקדמו מעבר לשורה 1 וידפיסו No Solution.!
הפתרון הנכון ב-OOP: לשמור את גודל הלוח כמשתנה מופע פרטי (boardSize) ב-Board ולהעבירו לכל Queen בעת האתחול.
⚔️ וריאציות המבחנים המרכזיות על 8 המלכות:
  • 1. צריחים ומלכות מפוזרות (`Rook` + `Queen`): צריח מאיים רק בשורה (row = testRow) ואינו מאיים באלכסון. מלכודת הבדיקה הדו-כיוונית: כאשר מפזרים על הלוח גם צריחים וגם מלכות, אם כלי משמאל הוא צריח וכלי מימינו הוא מלכה, בדיקת neighbor canAttack: row x: column תשאל את הצריח אם הוא תוקף את המלכה (והצריח ישיב false על אלכסון!), למרות שהמלכה עצמה תוקפת אלכסונית את הצריח שמשמאלה! לכן ב-Queen>>canAttack:x: או בבדיקת המלכה מול שכניה יש לוודא אי-איום דו-כיווני!
  • 2. כלי משולב "צריח+סוס" (`KnightRook`): מוסיפים ב-canAttack:x: בדיקת איום פרש: ((columnDifference = 1 and: [(testRow - row) abs = 2]) or: [columnDifference = 2 and: [(testRow - row) abs = 1]]).
  • 3. מלכות מוגבלות טווח באלכסון (עד מרחק $K$): תנאי האלכסון מתקיים רק אם columnDifference <= K.
🧊 לוח שחמט תלת-ממדי $N \times N \times N$ ($N^2$ מלכות): להצבת $N^2$ מלכות במרחב תלת-ממדי כך שאף מלכה אינה מאיימת על אחרת, מקצים לכל מלכה זוג קבוע (row, col) בשרשרת של $N^2$ מלכות והן בוחרות מפלס lev ($1..N$). עבור $d_x = |row - i|, d_y = |col - j|, d_z = |lev - k|$, איום מרחבי מתקיים אם:

9.1 ★ ייצוג מחלקה כעצם, שרשרת class, סיווג למטה-רמות ו-5 רמות עצמים

מכיוון שב-Smalltalk כל דבר הוא עצם וכל עצם הוא מופע של מחלקה, גם מחלקה היא עצם — והמחלקה שלה נקראת מטה-מחלקה (`Metaclass`): מחלקה שהמופעים שלה הם מחלקות!

🔄 מעקב שרשרת ההודעה `class` ממופע סופי ועד ללולאה:
  • • רמה 1 (מופע סופי): true
  • • רמה 2 (מחלקה): true class → True
  • • רמה 3 (מטה-מחלקה): true class class → True class
  • • רמה 4: true class class class → Metaclass
  • • רמה 5: true class class class class → Metaclass class
  • • 5 פעמים class: → Metaclass (ומכאן מתנדנד לנצח בין Metaclass ל-Metaclass class!)
🎭 סיווג עצמים לשלוש שכבות מהותיות: בדוגמת המחזות ("מקבת", "אותלו" $\in$ Play) והרומנים ("1984", "אוליבר טוויסט" $\in$ Novel):
1. מופעים סופיים (`Terminal Instances` / `Urelements`): עצמים פשוטים שאינם יכולים לייצר עצמים נוספים (רמה 1 – כגון true, 3@4 או "אוליבר טוויסט").
2. מחלקות (`Classes` / `Instantiable Objects`): עצמים המייצרים מופעים סופיים (רמה 2 – כגון True, Point, Novel, Play).
3. מטה-מחלקות (`Metaclasses`): עצמים שהמופעים שלהם הם מחלקות (רמות 3–5).
מספר הרמות במערכת שפות מייצגות מאפייני הארכיטקטורה והמגבלה ההנדסית שהובילה לרמה הבאה (שאלת מבחן!)
1. מערכת בת רמה 1 (עצמים בלבד) Self, JavaScript (Prototypes) מערכת שטוחה ללא מחלקות כלל. כל עצם מתאר את עצמו ומופעים חדשים נוצרים באמצעות שכפול (Cloning) של עצם אב-טיפוס (`Prototype`).
2. מערכת בת 2 רמות Eiffel, C++ יש מופעים ויש מחלקות המתארות אותם, אך המחלקות אינן עצמים בזמן ריצה ואינן מגיבות להודעות (יצירה נעשית באופרטור שפה קשיח).
3. מערכת בת 3 רמות Smalltalk-76, Little Smalltalk, Java כל המחלקות הן מופעים של מטה-מחלקה יחידה בלבד (`Class`) (שהיא מופע של עצמה). המגבלה הקריטית (שאלת מבחן!): מכיוון שכל המחלקות הן מופעים של אותה מחלקה יחידה Class, לכל המחלקות יש אותו פרוטוקול ואותו מימוש בדיוק של מתודות מחלקה (כגון new) ואי אפשר להגדיר מתודות-מחלקה או בנאים ייחודיים לכל מחלקה בנפרד (כגון Point x:y: או Color blue)!
4. מערכת בת 4 רמות LOOPS, ObjVlisp (CLOS) מאפשרת להגדיר מטה-מחלקות מפורשות (למשל MetaNovel עם משתנה מופע n_novels ומתודות יצירה ייחודיות), וכל המטה-מחלקות הן מופעים של מטה-מחלקה גנרית יחידה Metaclass (שהיא מופע של עצמה).
5. מערכת בת 5 רמות (Implicit Metaclasses) Squeak, Smalltalk-80 לכל מחלקה (כולל Metaclass עצמה!) נוצרת אוטומטית מטה-מחלקה אנונימית פרטית שבה היא המופע היחיד (Color class); כל המטה-מחלקות (כולל Metaclass class) הן מופעים של Metaclass!

9.2 ★ עשרת חוקי המודל ב-Squeak, ההיררכיה המקבילה ומסלול איתור new ו-blue

היררכיית המטה-מחלקות המקבילה להיררכיית המחלקות (חוק 7), נקודת המפגש ב-Class וסגירת המעגל ב-Metaclass (חוקים 8–10)

📜 10 החוקים של מודל העצמים והמטה-מחלקות ב-Squeak:

חוקים 1–5 (מודל העצמים הבסיסי): 1. כל דבר הוא עצם.
2. כל עצם הוא מופע של מחלקה.
3. לכל מחלקה יש מחלקת-על (למעט השורש ProtoObject שמחלקת-העל שלו היא nil).
4. הכל קורה באמצעות שליחת הודעות.
5. איתור מתודות (Method Lookup) מתחיל במחלקת המקבל ועולה בשרשרת הירושה.
חוקים 6–10 (חוקי המטה-מחלקות): 6. כל מחלקה היא מופע יחיד של מטה-מחלקה אנונימית (Color class).
7. היררכיית המטה-מחלקות מקבילה להיררכיית המחלקות!
8. כל מטה-מחלקה יורשת מ-Class (דרך ProtoObject class) ומ-Behavior.
9. כל מטה-מחלקה היא מופע של המחלקה Metaclass.
10. המטה-מחלקה של Metaclass (Metaclass class) היא מופע של Metaclass!

🏆 שאלת הבחינה הקלאסית: מסלול איתור המתודה TranslucentColor new מול TranslucentColor blue:

  • עבור TranslucentColor new: (1) המקבל (self) הוא עצם המחלקה TranslucentColor; (2) החיפוש מתחיל במחלקה של המקבל שהיא המטה-מחלקה TranslucentColor class (ולא ב-Color!); (3) החיפוש מטפס בשרשרת המטה-מחלקות: TranslucentColor class → Color class → Object class → ProtoObject class → Class → ClassDescription → Behavior; (4) המתודה new נמצאת ב-Behavior, ומכיוון שהיא פועלת על self (שהוא TranslucentColor), היא מייצרת ומחזירה מופע של TranslucentColor!
  • עבור TranslucentColor blue: החיפוש מתחיל ב-TranslucentColor class, עולה ל-Color class, מוצא שם את blue (שמחזירה מופע שמור של צבע כחול אטום רגיל). כדי ש-TranslucentColor blue תחזיר כחול שקוף יש לדרוס את blue ב-TranslucentColor class!
  • כותרת ה-Inspector: מציגה תמיד את שם המחלקה של העצם הנבחן: עבור Color blue הכותרת היא Color, ועבור המחלקה Color הכותרת היא Color class!

9.3 ★ מחלקות הליבה (Behavior, ClassDescription, Class, Metaclass), 5 סוגי המשתנים ושאלות המבחנים

1. Behavior (יורשת מ-Object) מגדירה את המינימום ההכרחי למחלקה שמייצרת מופעים: שומרת 3 משתני מופע (superclass, methodDict, format), מקמפלת מתודות ומממשת את מתודות היצירה new, basicNew, new:, basicNew: ותשאול הירושה (superclass, subclasses, allSuperclasses, allInstances).
2. ClassDescription (יורשת מ-Behavior) מחלקה מופשטת המוסיפה את התשתית הנדרשת ל-System Browser: שמות למשתני המופע (instanceVariables), ארגון מתודות בפרוטוקולים (organization), תיעוד ומחיקת/הדפסת מחלקה. ממנה מתפצלות שתי אחיות: Class ו-Metaclass!
3. Class (יורשת מ-ClassDescription) מגדירה את ההתנהגות המשותפת לכל המחלקות הרגילות (בעלות שם): מוסיפה את שם המחלקה (name), מילון משתני המחלקה (classPool), מאגרים משותפים (sharedPools) ותתי-מחלקות (subclasses). ממנה יורשת ProtoObject class!
4. Metaclass (יורשת מ-ClassDescription) מגדירה את התנהגותן של מטה-מחלקות אנונימיות: שומרת משתנה מופע thisClass (המצביע לעצם המחלקה היחיד שלה, למשל מ-Color class אל Color!). כל המטה-מחלקות הן מופעים של Metaclass!
סוג המשתנה אות ראשונה היכן מוגדר? למי הוא משותף ומי ניגש אליו ישירות?
1. משתנה מופע (Instance Variable) קטנה (x) בהגדרת המחלקה (instanceVariableNames:) עותק פרטי לכל מופע של המחלקה (ותתי-המחלקות). נגיש למתודות המופע של המחלקה ותתי-מחלקותיה בלבד.
2. משתנה מופע של מחלקה (Class Instance Variable) קטנה (count) בהגדרת המטה-מחלקה (במצב class ב-Browser) עותק פרטי ונפרד לכל עצם-מחלקה ולכל תת-מחלקה (כמו ב-Dog / Hyena). נגיש למתודות המחלקה בלבד!
3. משתנה מחלקה (Class Variable) גדולה (Count) בהגדרת המחלקה (classVariableNames:) עותק יחיד משותף למחלקה, לכל תתי-המחלקות ולכל מופעיהן. נגיש גם ממתודות מופע וגם ממתודות מחלקה!
4. מאגר משותף (Pool Dictionary) גדולה תת-מחלקה של SharedPool (תחת poolDictionaries:) משותף לקבוצת מחלקות המציינות את המאגר בהגדרתן (גם ללא קשר ירושה ביניהן).
5. משתנה גלובלי (Global Variable) גדולה (Transcript) במילון המערכת Smalltalk (SystemDictionary) נגיש מכל מקום במערכת (כל המחלקות עצמן שמורות כמשתנים גלובליים במילון Smalltalk!).

🎯 4 שאלות המבחנים הקלאסיות על מודל 5 הרמות ומטה-מחלקות:

  1. מתי מתקיים aCheck class class == aCheck?
    תשובה: אך ורק עבור 2 עצמים בכל המערכת: עבור המחלקה Metaclass (ברמה 4, כי Metaclass class class == Metaclass) ועבור המטה-מחלקה שלה Metaclass class (ברמה 5, כי Metaclass class class class == Metaclass class)!
  2. היכן נשבר חוק 7 של הקבלת הירושה (מתי aCheck superclass class ~= aCheck class superclass)?
    תשובה: בשני מקרים: (א) עבור שורש העץ ProtoObject: כי ProtoObject superclass הוא nil (ו-nil class הוא UndefinedObject), בעוד ProtoObject class superclass הוא המחלקה Class! (ב) עבור מטה-מחלקות (כגון Object class): כי מחלקת-העל שלהן היא מטה-מחלקה (שמחלקתה Metaclass), בעוד המחלקה שלהן היא Metaclass שמחלקת-העל שלה היא ClassDescription!
  3. מדוע הביטוי TranslucentColor isKindOf: Color מחזיר false (שאלת מלכודת קלאסית!)?
    תשובה: כי המקבל של isKindOf: כאן הוא עצם המחלקה TranslucentColor (ולא מופע שלה!), והמחלקה של TranslucentColor היא TranslucentColor class שיורשת מ-Color class → ... → Class → Object (ואינה יורשת מ-Color!). לעומת זאת: TranslucentColor new isKindOf: Color מחזיר true, וכן TranslucentColor isKindOf: Color class (או isKindOf: Class) מחזיר true!
  4. מימוש מתודות הבחינה level (רמת העצם 1..5) ו-depth (עומק בעץ הירושה): 
    // חישוב רמת העצם (1=מופע סופי, 2=מחלקה רגילה, 3=מטה-מחלקה, 4=Metaclass, 5=Metaclass class):
Object >> level
    self == (Metaclass class) ifTrue: [^ 5].
    self == Metaclass ifTrue: [^ 4].
    ^ (self class level) - 1

// חישוב עומק מחלקה בעץ הירושה (ProtoObject בעומק 0):
Behavior >> depth
    self superclass isNil ifTrue: [^ 0].
    ^ self superclass depth + 1
