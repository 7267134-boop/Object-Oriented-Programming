ייצוג מחלקה באמצעות עצם ושרשרת ההודעה class

אם כל דבר בשפת Smalltalk הוא עצם, וכל עצם הוא מופע של מחלקה — לאיזו מחלקה שייכת המחלקה עצמה, מדוע מחלקה חייבת להתקיים כעצם חי בזיכרון בזמן ריצה, וכיצד נמנעת רגרסיה אינסופית של יצרני מחלקות?

🧭

מודל מנטלי: כש"הכל הוא עצם" פוגש את "כל עצם הוא מופע של מחלקה"

במהלך הקורס הכרנו את שתי אבני היסוד של פילוסופיית ה-Pure OOP בשפת Smalltalk: ראשית, כל ישות במערכת היא עצם (מספרים, מחרוזות, צורות גרפיות, בלוקים — ואפילו מחלקות עצמן!). שנית, כל עצם במערכת הוא מופע (Instance) של מחלקה כלשהי הקובעת את מבנהו ואת התנהגותו. חיבור שני הכללים הללו מוביל לשאלה המרתקת ביותר במודל העצמים: אם מחלקה היא בעצמה עצם חי בזיכרון, של איזו מחלקה היא מופע? התשובה היא מֶטַה־מחלקה (Metaclass) — מחלקה שתפקידה לתאר ולייצר מחלקה!

💎 1. מחלקה היא עצם חי בזיכרון

ב-Smalltalk מחלקה אינה רק תבנית הידור סטטית; היא עצם אמיתי בזמן ריצה שמקבל הודעות (כמו new, superclass או subclasses) ומחזיק מצב והתנהגות משלו.

🪞 2. מטה-מחלקה אנונימית ויחידנית

לכל מחלקה (כגון True או Color) נוצרת אוטומטית מטה-מחלקה חסרת שם עצמאי, שהגישה אליה נעשית ע"י שליחת ההודעה האונרית class למחלקה (True class).

♾️ 3. לולאת Metaclass עוצרת אינסוף

במקום אינסוף של מטה-מטה-מחלקות, כל המטה-מחלקות הן מופעים של Metaclass, שנסגרת במעגל דו-כיווני עם המטה-מחלקה שלה Metaclass class!

1. מדוע מחלקה חייבת להיות מיוצגת כעצם חי בזמן ריצה?

זהות, מצב והתנהגות של מחלקה, קישור דינמי (Dynamic Binding), וחקירת עצמים גנרית (Reflection).

חוקר מחלקות

כל עצם בתכנות מונחה עצמים מתאפיין בשלושה מרכיבים: זהות ייחודית (Identity), מצב (State) והתנהגות (Behavior). מחלקה היא ישות המגדירה את הממשק של מופעיה, את השדות שהם שומרים ואת המתודות שהם מריצים. אך מדוע לא להסתפק בכך שהמחלקה תהיה הצהרה סטטית עבור המהדר בלבד, ומדוע חשוב כל כך לייצג את המחלקה עצמה כעצם בזיכרון בזמן ריצה? קיימות לכך שלוש סיבות הנדסיות מכריעות:

א קישור דינמי ושיתוף זיכרון

המתודה בפועל שמורצת בתגובה להודעה נקבעת בזמן ריצה לפי המחלקה של העצם המקבל (Dynamic Binding). מאחר שטבלת החיבור בין הודעות למתודות (methodDict) זהה לכל המופעים של אותה מחלקה, הגיוני לשתף אותה במקום לשכפל אותה בכל מופע: כל מופע מחזיק מצביע יחיד אל עצם המחלקה שלו בזיכרון.

ב מצב והתנהגות של המחלקה עצמה

לעצם המחלקה יש מצב משלו (ממי היא יורשת superclass, מילון המתודות methodDict, רשימת שמות משתני המופע instVarNames, מילון משתני המחלקה classPool) והתנהגות משלו (יצירת מופעים ב-new, הוספת מתודה חדשה בזמן ריצה, החזרת תתי-המחלקות subclasses).

ג רפלקציה וחקירת עצמים גנרית

כאשר המחלקה היא עצם, ניתן לחקור ולשנות כל עצם בזמן ריצה מבלי להכיר מראש את הממשק שלו — על ידי שליחת הודעה לעצם כדי לקבל את עצם המחלקה שלו, ותשאול עצם המחלקה על שדותיו ומתודותיו.

האנטומיה של עצם, עצם-מחלקה ומטה-מחלקה בזיכרון (Dynamic Binding & Reflection) שיתוף methodDict והפרדת Instance Side מ-Class Side
📌 הקבלה לשפת Java: פונקציית assignField רפלקטיבית Reflection

גם בשפות כמו Java ניתן לבקש מעצם o את עצם המחלקה שלו באמצעות שליחת ההודעה o.getClass(), ולשלוח לתוצאה c הודעות כמו getField כדי לעדכן שדה של העצם מבלי להכיר את הטיפוס שלו מראש: 

void assignField(Object o, String fieldName, Object value) {
    Class c = o.getClass();                 // שולח הודעה לעצם o ומקבל עצם c המייצג את מחלקתו
    Field f = c.getField(fieldName);        // שולח הודעה לעצם המחלקה c כדי לשלוף את השדה
    f.set(o, value);                        // מציב את הערך החדש בשדה של העצם o
}

שאלת המפתח: מאחר שהערך המוחזר מ-o.getClass() (או מ-anObject class ב-Smalltalk) הוא בעצמו עצם חי O1 המייצג את המחלקה, גם העצם O1 נוצר ממחלקה כלשהי המיוצגת על ידי עצם O2! מה יקרה אם נשלח class שוב ושוב (anObject class class class...)?

2. מעקב שרשרת ההודעה class: מ-true ועד ללולאה הסגורה של Metaclass

שבעת שלבי המעבר מרמה 1 ועד רמה 5, מחזוריות מאורך 2, וצבירת העצמים לתוך קבוצת Set.

מדרגות class

ב-Smalltalk, מחלקה שהמופעים שלה הם מחלקות נקראת מֶטַה־מחלקה (Metaclass), והיא נוצרת באופן אוטומטי בכל פעם שמגדירים מחלקה חדשה. חשוב להדגיש: מחלקה כלשהי והמטה-מחלקה שלה הן שתי מחלקות נפרדות לחלוטין — כאשר אנו לוחצים ב-System Browser על הכפתור class (ומעבירים אותו ממצב Instance למצב Class), אנו למעשה צופים ועורכים מחלקה אחרת: את המטה-מחלקה! מאחר שלמטה-מחלקות אין שם גלובלי משלהן (הן אנונימיות), אנו ניגשים אליהן באמצעות שליחת ההודעה האונרית class אל עצם המחלקה.

🎯 דגש מרכזי לשאלות מעקב: איסוף איברי שרשרת class לתוך Set והזהות x class class == x

כאשר מכניסים בלולאה את איברי שרשרת ה-class לתוך קבוצה (Set, שאינה שומרת כפילויות), גודל הקבוצה הסופי תלוי בשאלה האם התחלנו ממופע סופי ברמה 1 או ממחלקה ברמה 2: 

"מקרה א': מתחילים מהמופע הסופי 3 (רמה 1) ורצים 10 פעמים:"

9.1 ייצוג מחלקה באמצעות עצם ושרשרת ההודעה class

כל מה שצריך לדעת מאפס: מדוע מחלקה ב-Smalltalk מיוצגת כעצם חי בזמן ריצה, מהי מטה-מחלקה אנונימית, וכיצד פועלת שרשרת 7 הצעדים של true class... עד סגירת המעגל ב-Metaclass.

1. מדוע מחלקה היא עצם חי בזיכרון, ומהי מטה-מחלקה (Metaclass)?

חיבור שני חוקי היסוד: כל דבר ב-Smalltalk הוא עצם, וכל עצם הוא מופע של מחלקה.

  • קישור דינמי (Dynamic Binding) ושיתוף זיכרון: המתודה שמורצת בתגובה להודעה נקבעת בזמן ריצה לפי המחלקה של המקבל. מאחר שמילון המתודות (methodDict) משותף לכל מופעי אותה מחלקה, כל מופע מחזיק מצביע יחיד אל עצם המחלקה שלו.
  • מצב והתנהגות של המחלקה: לעצם המחלקה יש מצב משלו (מצביע למחלקת-העל superclass, מילון מתודות methodDict, רשימת שמות משתני מופע) והתנהגות משלו (יצירת מופעים באמצעות new, חקירת מבנה העצם ברפלקציה, כמו o.getClass() ב-Java).
  • מטה-מחלקה (Metaclass): מאחר שגם מחלקה היא עצם, היא חייבת להיות מופע של מחלקה. מחלקה שהמופעים שלה הם מחלקות נקראת מטה-מחלקה.
  • הפרדה ואנונימיות: בכל פעם שמגדירים מחלקה (כגון Color או True), נוצרת עבורה אוטומטית מטה-מחלקה נפרדת וחסרת שם גלובלי עצמאי. ניגשים אליה ע"י שליחת ההודעה האונרית class למחלקה: Color class (וב-System Browser לחיצה על כפתור class עוברת מעריכת המחלקה לעריכת המטה-מחלקה שלה).

9.1 סיכום בזק: מחלקה כעצם ושרשרת ההודעה class

מחלקה כעצם ומטה-מחלקה

• קישור דינמי ורפלקציה: כל מופע מצביע לעצם המחלקה שלו (המחזיק superclass ו-methodDict).

• מטה-מחלקה (Metaclass): מחלקה שהמופעים שלה הם מחלקות; אנונימית ונוצרת אוטומטית (גישה דרך Color class).

שרשרת class וכללי זהב

• true (1) ➔ True (2) ➔ True class (3) ➔ Metaclass (4) ⇄ Metaclass class (5).

• x class class == x מתקיים רק עבור Metaclass ו-Metaclass class. גודל Set מ-3 הוא 5 (מ-3 class הוא 4).

נפתח בדוגמה קלאסית ומוחשית: נניח שיש לנו במערכת שתי מחלקות בשם "מחזה" (Play) ו-"רומן" (Novel), אשר שתיהן יורשות מהמחלקה Object ושתיהן מופעים של המחלקה "מחלקה" (Class) — כאשר Class עצמה יורשת מ-Object והיא מופע של עצמה. המחזות של ויליאם שייקספיר (Macbeth, As You Like It, Othello) הם מופעים של המחלקה Play, והספרים (War & Peace, Oliver Twist, 1984) הם מופעים של המחלקה Novel.

גרף העצמים של Play, Novel, Object ו-Class וחלוקתם ל-3 שכבות חץ רציף = יורש מ- (superclass) | חץ מקווקו = מופע של (class)
1. חלוקת כל העצמים במערכת (Objects): קבוצת כל העצמים מתחלקת לעצמים פשוטים / מופעים סופיים (Terminal Instances / Non-instantiable objects) שאינם יכולים לייצר עצמים נוספים (כגון Oliver Twist או Othello), מול עצמים המייצגים מחלקות (Classes / Instantiable objects) המסוגלים לייצר מופעים חדשים.
2. חלוקת קבוצת המחלקות (Classes): קבוצת המחלקות עצמה מתחלקת למחלקות רגילות שהמופעים שלהן הם מופעים סופיים בלבד (כגון Novel, Play ו-Object), מול מטה-מחלקות (Metaclasses) שהמופעים שלהן הם מחלקות (בדוגמה שלעיל: המחלקה Class).

2. התפתחות מערכות העצמים: מרמה בודדת (Self) ועד 5 רמות (Squeak)

מכונת הזמן 1–5

לכל שפת תכנות מונחית עצמים יש מודל עצמים (Object Model) הקובע כמה רמות של עצמים ומחלקות קיימות בה. מעבר שיטתי על חמשת המודלים (מרמה 1 ועד רמה 5) מבהיר בדיוק איזו בעיה הנדסית פתרה כל רמה:

1. מערכת בת רמה 1 (Prototype-based) Self / JavaScript

מבנה: מערכת "שטוחה" של עצמים בלבד ללא מחלקות כלל. כל עצם מתאר את עצמו באמצעות טבלת חריצים (Slots) המתאימה שמות לערכים ולמתודות.
יצירה ושיתוף: עצם חדש נוצר ע"י שכפול (Cloning) של עצם אב-טיפוס קיים (Novel Prototype). שיתוף מתודות מתבצע ע"י מצביע PARENT לעצם תכונות משותף (Novel Traits המכיל STORE, שמצביע ל-Object Traits המכיל PRINT).

2. מערכת בת 2 רמות (מחלקות סטטיות) Eiffel / C++

מבנה: יש עצמים ויש מחלקות המתארות אותם, אך המחלקות אינן עצמים! הן קיימות כמידע סטטי בזמן הידור בלבד ואינן מיוצגות בזיכרון בזמן ריצה.
מגבלה מרכזית: מאחר שהמחלקה אינה מופע של מחלקה, לא ניתן לשלוח למחלקה הודעה בזמן ריצה, לא ניתן להעביר מחלקה כפרמטר דינמי, ויצירת מופעים נעשית בפקודה תחבירית קבועה.

3. מערכת בת 3 רמות (מטה-מחלקה יחידה) Smalltalk-76 / Little ST

מבנה: גם העצמים וגם המחלקות הם עצמים. כל המחלקות מתוארות ע"י מטה-מחלקה יחידה אחת (Class), שהיא מופע של עצמה ויורשת מ-Object.
יתרון: מונע אינסופיות בתהליך זיהוי השייכות למחלקה.
⚠️ המגבלה הקריטית: בגלל שיש רק מטה-מחלקה אחת (Class), לכל המחלקות במערכת יש מבנה והתנהגות זהים לחלוטין! יש רק דרך אחת לבצע new, ואי אפשר להגדיר מתודות מחלקה או בנאים ייחודיים לכל מחלקה (כמו Point x:y:) או משתני מחלקה פרטניים!

4. מערכת בת 4 רמות (מטה-מחלקות מותאמות) LOOPS / ObjVlisp (Lisp)

מבנה: פותרת את מגבלת 3 הרמות: לכל מחלקה (כגון Novel) יש מטה-מחלקה (Meta Novel) המגדירה פרטנית את מתודות המחלקה ומשתני המחלקה שלה (new, n_novels, add_novel), וכל המטה-מחלקות הן מופעים של מטה-מחלקה גנרית יחידה (Meta Class) שהיא מופע של עצמה.
המעבר ל-5 רמות: ב-Smalltalk שבה לכל מחלקה נוצרת אוטומטית מטה-מחלקה יחידנית (Singleton) משלה, גם למחלקה הגנרית Metaclass חייבת להיות מטה-מחלקה פרטית משלה (Metaclass class)!

אנימטור Lookup
חמשת חוקי הבסיס של מודל העצמים (Rules 1–5) ב-Smalltalk אבני היסוד של השפה
Rule 1 כל דבר הוא עצם Everything is an object — כולל מספרים, צבעים (Color blue) ומחלקות עצמן.

Color blue                          "===> Color blue"

"כלל 2: כל עצם הוא מופע של מחלקה — הצבע הכחול הוא מופע של Color:"
Color blue class                    "===> Color"

"קביעת שקיפות (alpha: 0.4) מחזירה עצם צבע שקוף-למחצה שהוא מופע של TranslucentColor:"
(Color blue alpha: 0.4) class       "===> TranslucentColor"

"יצירת אליפסה גרפית בצבע כחול שקוף-למחצה והצגתה בעולם של Squeak:"
EllipseMorph new color: (Color blue alpha: 0.4); openInWorld.

"כלל 3: לכל מחלקה יש מחלקת-על (וב-Squeak מעל Object נמצאת ProtoObject שמעליה nil):"
TranslucentColor superclass         "===> Color"
Color superclass                    "===> Object"
Object superclass                   "===> ProtoObject"
ProtoObject superclass              "===> nil"

• כאשר שולחים Color blue אל עצם המחלקה Color, מופעלת מתודת המחלקה Color class >> blue המחזירה את עצם הצבע הכחול השמור מראש במשתנה המחלקה Blue (המכיל ערכי RGB של כחול).
• לעומת זאת, כאשר שולחים aColor blue אל מופע מסוג Color, מופעלת מתודת המופע Color >> blue המחזירה מספר ממשי בין 0.0 ל-1.0 המייצג את כמות מרכיב הצבע הכחול ב-RGB של אותו צבע!

2. תהליך איתור המתודה class ומתודות הבדיקה והשייכות (isKindOf:, canUnderstand:)

מעקב אחר translucentBlue class ומימוש מתודות הבדיקה במחלקות Object ו-Behavior.

בדיקות שייכות
מסלול איתור המתודה class בעת שליחתה אל המופע translucentBlue Rule 5: Method Lookup
בדיקת שייכות עם isKindOf: על המופע translucentBlue: 
translucentBlue := Color blue alpha: 0.4.
translucentBlue isKindOf: TranslucentColor   "===> true"
translucentBlue isKindOf: Color              "===> true"
translucentBlue isKindOf: Object             "===> true"
translucentBlue isKindOf: Color class        "===> false!"
מדוע השורה הרביעית מחזירה false?

המופע translucentBlue הוא מופע של TranslucentColor (ששייכת להיררכיית המחלקות TranslucentColor → Color → Object → ProtoObject). הוא אינו מופע של המטה-מחלקה Color class (שהמופע היחיד שלה הוא המחלקה Color עצמה!).

מימוש מתודות הרפלקציה לבדיקת שייכות ומתודות ב-Object וב-Behavior:

"1. במחלקה Object — בדיקת שייכות למחלקה ובדיקת תגובה להודעה:"
Object >> isMemberOf: aClass
    "מחזירה true אם ורק אם המקבל הוא מופע ישיר של aClass (ללא ירושה)"
    ^self class == aClass

Object >> isKindOf: aClass
    "מחזירה true אם המקבל הוא מופע ישיר של aClass או של תת-מחלקה היורשת מ-aClass"
    (self isMemberOf: aClass) ifTrue: [ ^true ].
    ^self class inheritsFrom: aClass

Object >> respondsTo: aSymbol
    "מחזירה true אם מחלקתו של המקבל (או אחת ממחלקות-העל שלה) מבינה את הבורר aSymbol"
    ^self class canUnderstand: aSymbol

"2. במחלקה Behavior — בדיקת קיום מתודה במחלקה הנוכחית מול שרשרת הירושה כולה:"
Behavior >> includesSelector: aSymbol
    "בודקת אך ורק במילון המתודות המקומי (methodDict) של המחלקה הנוכחית!"
    ^self methodDict includesKey: aSymbol

Behavior >> canUnderstand: aSymbol
    "בודקת רקורסיבית האם מופעים של המחלקה מבינים את aSymbol (במחלקה או במחלקות-העל שלה)"
    (self includesSelector: aSymbol) ifTrue: [ ^true ].
    superclass ifNil: [ ^false ].
    ^superclass canUnderstand: aSymbol

1. חמשת חוקי הבסיס של Smalltalk (Rules 1–5)

חמשת הכללים הראשונים המגדירים את עולם העצמים ואיתור המתודות:

  • Rule 1 (הכל עצם): כל דבר במערכת הוא עצם (Color blue, מספרים, מחלקות).
  • Rule 2 (מופע של מחלקה): כל עצם הוא מופע של מחלקה (Color blue class == Color, ואילו (Color blue alpha: 0.4) class == TranslucentColor).
  • Rule 3 (מחלקת-על): לכל מחלקה יש מחלקת-על יחידה (TranslucentColor → Color → Object → ProtoObject → nil).
  • Rule 4 (הכל בהודעות): כל חישוב מתבצע באמצעות שליחת הודעות לעצמים (שימו לב: Color blue היא מתודת מחלקה המחזירה את הצבע הכחול מ-Blue, ואילו aColor blue על מופע מחזירה את מרכיב הכחול ב-RGB).
  • Rule 5 (איתור מתודות בירושה): חיפוש מתודה מבצע קפיצה אחת בלבד על חץ מופע אל מחלקת המקבל (self class) ומטפס בשרשרת superclass. ב-translucentBlue class החיפוש עובר ב-TranslucentColor → Color → Object (שם נמצאת המתודה class ומחזירה TranslucentColor). אם החיפוש מגיע ל-nil מעל ProtoObject ללא ממצא — נשלחת למקבל ההודעה doesNotUnderstand:.

2. מתודות הבדיקה והשייכות ב-Object וב-Behavior

ארבע מתודות רפלקציה שמופיעות באופן קבוע בשאלות כתיבת קוד:

Object >> isMemberOf: aClass      ^self class == aClass
Object >> isKindOf: aClass        (self isMemberOf: aClass) ifTrue: [^true]. ^self class inheritsFrom: aClass
Object >> respondsTo: aSymbol     ^self class canUnderstand: aSymbol

Behavior >> includesSelector: s   ^self methodDict includesKey: s   "רק במחלקה הנוכחית!"
Behavior >> canUnderstand: s      (self includesSelector: s) ifTrue: [^true]. superclass ifNil: [^false]. ^superclass canUnderstand: s

מדוע לכל מחלקה ב-Smalltalk קיימת מטה-מחלקה אנונימית יחידנית משלה, כיצד הקבלת הירושה מאפשרת ירושה ודריסה של מתודות מחלקה, והיכן בדיוק מאותרת המתודה new בעת יצירת מופע חדש?

🧭

מודל מנטלי: אפקט הראי — היררכיית המטה-מחלקות משקפת את היררכיית המחלקות!

כיצד שפת Smalltalk מצליחה לשלב בין שני עולמות: מצד אחד לאפשר לכל מחלקה להגדיר מתודות מחלקה (Class Methods) ייחודיות משלה (כמו Color blue או Array new: 4), ומצד שני לאפשר לתת-מחלקה לרשת ולדרוס את מתודות המחלקה של מחלקת-העל שלה (כמו TranslucentColor blue)? הסוד טמון בשילוב שבין חוק 6 (לכל מחלקה יש מטה-מחלקה אנונימית פרטית משלה) לבין חוק 7 (היררכיית הירושה של המטה-מחלקות מקבילה במדויק להיררכיית הירושה של המחלקות!).

🪞 חוק 6: מטה-מחלקה יחידנית

בכל יצירת מחלקה X נוצרת אוטומטית מטה-מחלקה אנונימית X class, והמחלקה X היא המופע היחיד (Singleton) שלה.

🛤️ חוק 7: הקבלת הירושה

אם TranslucentColor יורשת מ-Color, אזי TranslucentColor class יורשת מ-Color class!

🚀 איתור new ב-Behavior

חיפוש TranslucentColor new מתחיל ב-TranslucentColor class (ולא ב-Color!), מטפס עד Behavior, ומחזיר מופע של self.

1. חוק 6 וחוק 7: מטה-מחלקות אנונימיות וההיררכיה המקבילה

חמש עובדות היסוד של מטה-מחלקות, חקירת מחלקות בהודעות רפלקציה, והזהות aClass class superclass == aClass superclass class.

היררכיה מקבילה

לפי הכלל השישי (Rule 6: Every class is an instance of a metaclass), בכל פעם שאנו מגדירים מחלקה חדשה במערכת, נוצרת עבורה באופן אוטומטי מטה-מחלקה. נסכם את חמש העובדות היסודיות לגבי מטה-מחלקות:

  1. מטה-מחלקות הן מחלקות שהמופעים שלהן הם מחלקות.
  2. מטה-מחלקות נוצרות באופן אוטומטי ומשתמע (Implicit) כאשר מגדירים מחלקה חדשה.
  3. לכל מטה-מחלקה קיים בדיוק מופע אחד ויחיד (Singleton) — עצם המחלקה שהיא מתארת.
  4. מטה-מחלקות הן אנונימיות (חסרות שם גלובלי משלהן), בעוד שמשתנים גלובליים משמשים כשמות של מחלקות רגילות.
  5. ההתייחסות למטה-מחלקות מתבצעת באמצעות המופעים שלהן: שליחת ההודעה class למחלקה Color מחזירה את המטה-מחלקה שלה Color class, ושליחת class ל-Object מחזירה את Object class.

לפי הכלל השביעי (Rule 7: The metaclass hierarchy parallels the class hierarchy), היררכיית הירושה של המטה-מחלקות מקבילה להיררכיית הירושה של המחלקות. כלומר: מחלקת-העל של מטה-מחלקה כלשהי היא המטה-מחלקה של מחלקת-העל של המחלקה היחידה שלה!

ההיררכיה המקבילה של TranslucentColor והמטה-מחלקות שלה (Rules 6 & 7) TranslucentColor class superclass == Color class
⚠️ הבחנה קריטית בין "מופע של" לבין "תת-מחלקה של": שימו לב לקשר שבין TranslucentColor לבין TranslucentColor class: הראשונה היא מופע של השנייה, ואינה תת-מחלקה שלה! מחלקת-העל של TranslucentColor היא Color (ולכן TranslucentColor isKindOf: TranslucentColor class מחזיר true, אך TranslucentColor inheritsFrom: TranslucentColor class מחזיר false!).

2. שליחת הודעות למחלקות: איתור TranslucentColor blue ואיתור TranslucentColor new

כיצד תת-מחלקה יורשת ודורסת מתודות מחלקה, היכן מאותרת new, ומלכודת (Set new) new.

מעבדת new ו-blue

היות שמחלקות הן עצמים, מנגנון שליחת ההודעות למחלקות פועל בדיוק באותה הצורה שבה פועל מנגנון שליחת ההודעות לעצמים רגילים! איתור המתודה מתחיל במחלקה של העצם שקיבל את ההודעה — כלומר במטה-מחלקה של המחלקה שקיבלה את ההודעה — ואם המתודה אינה נמצאת שם, החיפוש עולה בהיררכיית הירושה של המטה-מחלקות:

🎨 מקרה א': TranslucentColor blue

ירושת מתודת מחלקה
  • המקבל: עצם המחלקה TranslucentColor (ולכן self = TranslucentColor).
  • קפיצת מופע: החיפוש מתחיל במטה-מחלקה TranslucentColor class. המתודה blue אינה מוגדרת בה כברירת מחדל.
  • טיפוס בירושה (חוק 7): החיפוש עולה למחלקת-העל Color class — שם נמצאת המתודה blue המחזירה את הצבע הכחול האטום (Color blue).
כיצד נגרום לכך ש-TranslucentColor blue תחזיר כחול בשקיפות 50%? נגדיר (נדרוס) מתודת מחלקה blue במטה-מחלקה TranslucentColor class: 
TranslucentColor class >> blue
    ^super blue alpha: 0.5   "או: ^Blue alpha: 0.5"

🚀 מקרה ב': TranslucentColor new

יצירת מופע חדש
  • מלכודת נפוצה: טעות לחפש את new ב-Color! החיפוש מתחיל במטה-מחלקה TranslucentColor class.
  • מסלול הטיפוס המלא: TranslucentColor class → Color class → Object class → ProtoObject class → Class → ClassDescription → Behavior!
  • מדוע נוצר מופע של TranslucentColor ולא של Behavior? משום ש-Behavior >> new מריצה ^self basicNew initialize, והפסאודו-משתנה self מצביע למקבל המקורי: TranslucentColor!
💡 דגש ממצגות הקורס על Color class >> new:
בפועל ב-Squeak, המטה-מחלקה Color class דורסת את new ושולחת ^self r: 0 g: 0 b: 0 (ששולחת self basicNew setRed: r green: g blue: b). כאשר שולחים TranslucentColor new, נוצר מופע של TranslucentColor אך השדה alpha שלו נותר לא מאותחל (nil)! התיקון הוא לדרוס ב-TranslucentColor class את r:g:b: כך שתאתחל גם ערך ברירת מחדל ל-alpha.

⚠️ מלכודת שליחת new למופע סופי: a := Set new. b := a new

מה יקרה אם נריץ a := Set new. b := a new? בשורה הראשונה נוצר ב-a מופע סופי (ברמה 1) של המחלקה Set. בשורה השנייה אנו שולחים את ההודעה new אל המופע a (ולא אל המחלקה Set!). החיפוש מתחיל ב-Set ומטפס בשרשרת: Set → HashedCollection → Collection → Object → ProtoObject → nil. שרשרת זו אינה עוברת דרך Behavior, ולכן נזרקת שגיאת MessageNotUnderstood: Set >> new! כדי ליצור מופע חדש מאותה מחלקה מתוך מופע קיים a, יש לכתוב b := a class new (או b := a species new).

9.4 חוקי המטה-מחלקות (Rules 6–7), ההיררכיה המקבילה ואיתור new

חמש עובדות היסוד על מטה-מחלקות, הקבלת עץ הירושה, וכיצד מתבצע חיפוש של מתודות מחלקה כמו blue ו-new.

1. חוק 6 וחוק 7: מטה-מחלקה אנונימית והקבלה בירושה

שני החוקים שמחברים בין מחלקות למטה-מחלקות שלהן:

  • Rule 6 (כל מחלקה היא מופע של מטה-מחלקה): לכל מחלקה נוצרת אוטומטית מטה-מחלקה אנונימית שיש לה בדיוק מופע אחד ויחיד (Singleton) — המחלקה עצמה! ניגשים אליה ע"י Color class. שימו לב: TranslucentColor היא מופע של TranslucentColor class (ולא תת-מחלקה שלה!).
  • Rule 7 (היררכיית המטה-מחלקות מקבילה להיררכיית המחלקות): לכל מחלקה רגילה מתקיים: aClass class superclass == aClass superclass class. לכן TranslucentColor class superclass הוא Color class, ומעליה Object class.
  • הודעות חקירה למחלקה: Color subclasses, TranslucentColor allSuperclasses, TranslucentColor instVarNames (מקומיים: #('alpha')), TranslucentColor allInstVarNames (כולל מורשים), ו-TranslucentColor selectors.

2. מסלול איתור TranslucentColor blue ו-TranslucentColor new

חיפוש הודעה שנשלחה למחלקה מתחיל תמיד במטה-מחלקה שלה!

  • איתור TranslucentColor blue: מתחיל ב-TranslucentColor class ➔ עולה ל-Color class ➔ מוצא את blue ומחזיר Color blue. לדריסה כך שיוחזר כחול שקוף (50%) מגדירים ב-TranslucentColor class: blue ^super blue alpha: 0.5.
  • איתור TranslucentColor new: מתחיל ב-TranslucentColor class (ולא ב-Color!) ➔ Color class ➔ Object class ➔ ProtoObject class ➔ Class ➔ ClassDescription ➔ ונמצא ב-Behavior >> new! המתודה מריצה ^self basicNew initialize עבור self = TranslucentColor, ולכן מוחזר מופע של TranslucentColor!
  • מלכודת (Set new) new: שליחת new למופע סופי (a := Set new. a new) זורקת MessageNotUnderstood: Set >> new כי החיפוש מטפס מ-Set ל-Object ואינו עובר דרך Behavior! התיקון: a class new.

1. חוקים 8, 9 ו-10 וארבע מחלקות הליבה (Behavior, ClassDescription, Class, Metaclass)

מפת העל השלמה של מודל 5 הרמות, חלוקת האחריות בין מחלקות הליבה, וניתוח שאלת מיזוג המחלקות.

נווט 10 החוקים
  • חוק 8 (Rule 8: Every metaclass inherits from Class and Behavior): כל מטה-מחלקה היא מחלקה, ולכן מטה-מחלקות יורשות מ-Class, שיורשת מ-ClassDescription, וזו יורשת מ-Behavior (שבעצמה יורשת מ-Object → ProtoObject). מדוע כלל 8 אינו סותר את כלל 7? כלל 7 קובע שלכל מחלקה שיש לה מחלקת-על, המטה-מחלקה שלה יורשת מהמטה-מחלקה של מחלקת-העל. אך לשורש עץ המחלקות (ProtoObject ב-Squeak, או Object בתרשים המופשט) אין מחלקת-על (superclass == nil)! לכן בנקודת השורש הזו, ProtoObject class יורשת מהמחלקה Class!
  • חוק 9 (Rule 9: Every metaclass is an instance of Metaclass): כל המטה-מחלקות (TranslucentColor class, Color class, Object class, Class class וכו') הן מופעים של המחלקה Metaclass. המחלקה Metaclass יורשת מהמחלקה המופשטת ClassDescription (במקביל ל-Class שאף היא יורשת מ-ClassDescription).
  • חוק 10 (Rule 10: The metaclass of Metaclass is an instance of Metaclass): גם למחלקה Metaclass יש מטה-מחלקה שהיא Metaclass class, ומכיוון שכל מטה-מחלקה היא מופע של Metaclass, גם Metaclass class היא מופע של Metaclass! (ולפי חוק 7, היות שמחלקת-העל של Metaclass היא ClassDescription, הרי שמחלקת-העל של Metaclass class היא ClassDescription class).
מפת העל השלמה של קשרי המופעים (class) והיררכיית הירושה (superclass) במודל 5 הרמות חץ רציף = ירושה | חץ מקווקו = מופע של

חלוקת האחריות המדויקת בין ארבע מחלקות הליבה:

1. Behavior (יורשת מ-Object) – ליבת ההרצה והיצירה מספקת את המינימום ההכרחי לכל עצם שיש לו מופעים (הן מחלקות והן מטה-מחלקות!). מחזיקה 3 משתני מופע קריטיים: superclass (מצביע למחלקת-העל), methodDict (מילון המתודות הממפה סמלי Symbol לאובייקטי CompiledMethod), ו-format (מספר המשתנים ומבנה המופע). מתודות מרכזיות: ממשק לקומפיילר, יצירת מופעים (new, basicNew, new:, basicNew:), וניווט ובדיקה (superclass, selectors, includesSelector:, canUnderstand:, inheritsFrom:).
2. ClassDescription (יורשת מ-Behavior) – מחלקה מופשטת משותפת מחלקה מופשטת המספקת את המבנה וההתנהגות הארגוניים המשותפים לשתי תתי-המחלקות שלה: Class ו-Metaclass. מוסיפה ל-Behavior את משתני המופע instanceVariables (מערך שמות משתני המופע) ו-organization (קטלוג פרוטוקולים של מתודות). מתודות מרכזיות: instVarNames, allInstVarNames, addInstVarName:, תיעוד, מעקב שינויים ב-Change Set וביצוע fileOut / fileIn.
3. Class (יורשת מ-ClassDescription) – מחלקות בעלות שם מייצגת את ההתנהגות והמבנה המשותפים לכל המחלקות הרגילות (בעלות שם גלובלי). מוסיפה את השדות: name (שם המחלקה כסימבול), subclasses (תתי-המחלקות), classPool (מילון משתני המחלקה classVariableNames:), sharedPools (מאגרים משותפים) וקטגוריית המערכת. מתודות מרכזיות: name, classVarNames, addClassVarName:, addSharedPool:.
4. Metaclass (יורשת מ-ClassDescription) – מטה-מחלקות אנונימיות המופעים שלה הם המטה-מחלקות האנונימיות (כולל Metaclass class עצמה!). קלה יותר מ-Class (אין לה שם עצמאי או classPool משלה), ומוסיפה את השדה thisClass המצביע אל עצם המחלקה היחיד (Singleton) שהיא מייצרת. מתודות מרכזיות: דריסת new ליצירת מופע יחיד בלבד, אתחול משתני מחלקה והפניית allClassVarNames אל theNonMetaClass. 
"1. מימוש new ב-Behavior (מופעל כששולחים new למחלקה רגילה כמו Point new):"
Behavior >> new
    ^self basicNew initialize

"2. דריסת new ב-Metaclass (מופעל כששולחים new למטה-מחלקה — אוכף מופע יחיד Singleton!):"
Metaclass >> new
    "למטה-מחלקה מותר ליצור מופע אחד בלבד (thisClass); ניסיון שני זורק שגיאה!"
    thisClass class ~~ self ifTrue: [ ^thisClass := self basicNew ].
    self error: 'A Metaclass should only have one instance!'

🎯 ניתוח הנדסי: האם ניתן למזג את מחלקות הליבה, וכיצד מאותרת Metaclass name?

א. האם ניתן למזג את Behavior ו-ClassDescription למחלקה אחת BehaviorClassDescription?
הדבר אפשרי מבלי לשבור את תפקוד המחלקות והמטה-מחלקות הרגילות (שכן גם Class וגם Metaclass יורשות משתיהן). החיסרון היחיד הוא פגיעה במודולריות וביכולת להגדיר תתי-מחלקות קלות-משקל של Behavior (עצמים בעלי מופעים למחקר/VM שאינם זקוקים לשמות משתנים, פרוטוקולים ו-Change Sets).

ב. האם ניתן למזג את Class ו-ClassDescription?
כאן קיימת בעיה ארכיטקטונית מהותית! המחלקה ClassDescription היא מחלקת-העל המשותפת של שתי מחלקות אחיות: Class ו-Metaclass. למטה-מחלקות (מופעי Metaclass) אין שם גלובלי משלהן ואין להן מילון משתני מחלקה (classPool) או sharedPools משלהן. אם נמזג את Class לתוך ClassDescription, או שכל מטה-מחלקה תיאלץ לרשת ולהחזיק שדות ומתודות של Class שאינם שייכים לה (בזבוז זיכרון ושבירת הפרדת האחריות), או ש-Metaclass תנותק מ-ClassDescription ונאבד את שיתוף הקוד ביניהן!

ג. כיצד שליחת Metaclass name מפעילה את Class >> name אף ש-Metaclass אינה יורשת מ-Class?
כאשר שולחים Metaclass name, המקבל הוא עצם המחלקה Metaclass, ולכן החיפוש מתחיל במחלקתו Metaclass class! משם החיפוש מטפס בשרשרת המטה-מחלקות: Metaclass class → ClassDescription class → Behavior class → Object class → ProtoObject class → Class! במילון המתודות של Class נמצאת המתודה Class >> name המחזירה #Metaclass!

5 סוגי משתנים
סוג המשתנה אות ראשונה היכן מוגדר ונשמר? מספר עותקים בזיכרון טווח הכרה (Scope)
1. משתנה מופע
(Instance Variable)		 אות קטנה (x, row) instanceVariableNames: בהגדרת המחלקה עותק נפרד ופרטי לכל מופע (עצם) של המחלקה ויורשיה מתודות מופע של המחלקה ותתי-המחלקות שלה בלבד (כמוס למופע הספציפי self!).
2. משתנה מופע של מטה-מחלקה
(Class Instance Variable)		 אות קטנה (count, z) instanceVariableNames: בהגדרת המטה-מחלקה (Dog class) עותק נפרד לכל עצם-מחלקה בעץ ההורשה (עותק ל-Dog ועותק נפרד ל-Hyena!) מתודות מחלקה (Class Methods) של המחלקה ותתי-המחלקות שלה בלבד (מופעים רגילים אינם מכירים אותו ישירות!).
3. משתנה מחלקה
(Class Variable)		 אות גדולה (Blue, A) classVariableNames: בהגדרת המחלקה (נשמר ב-classPool של Class) עותק אחד ויחיד המשותף למחלקה, למטה-מחלקה, לכל תתי-המחלקות ולכל מופעיהן! הן ממתודות מופע והן ממתודות מחלקה של המחלקה וכל תתי-המחלקות שלה.
4. משתנה מאגר משותף
(Pool Variable)		 אות גדולה (Cr, Lf) poolDictionaries: בהגדרת המחלקה (מוחזק ב-sharedPools) עותק יחיד במילון המאגר המשותף כל המחלקות (גם מעצי ירושה שונים!) שהצהירו על המאגר ב-poolDictionaries: שלהן.
5. משתנה גלובלי
(Global Variable)		 אות גדולה (Transcript) מילון המערכת הגלובלי Smalltalk עותק יחיד בכל תמונת הזיכרון (Image) מוכר מכל מקום במערכת כולה (כל מתודה, בלוק או Workspace).
דוגמת מונה המופעים של Dog ו-Hyena: משתנה מופע של מטה-מחלקה (count) מול משתנה מחלקה (classVariableNames:) עותק נפרד לכל מחלקה בעץ ההורשה! 
Object subclass: #Dog instanceVariableNames: '' classVariableNames: '' ...
Dog class instanceVariableNames: 'count'
Dog subclass: #Hyena instanceVariableNames: '' classVariableNames: '' ...

Dog class >> initialize   super initialize. count := 0.
Dog class >> new          count := count + 1. ^super new
Dog class >> count        ^count

Dog initialize. Hyena initialize.
Dog new. Dog new. Hyena new.
Dog count     "===> 2"
Hyena count   "===> 1 (עותק נפרד לעצם המחלקה Hyena!)"
מדוע Hyena count מחזיר 1 ו-Dog count נשאר 2? המשתנה count הוגדר כמשתנה מופע של המטה-מחלקה Dog class. מכיוון ש-Hyena class יורשת מ-Dog class (לפי חוק 7), היא יורשת את הגדרת השדה count. לכן לעצם המחלקה Dog יש תא count פרטי משלו (2), ולעצם המחלקה Hyena יש תא count נפרד משלו (1)!
מה היה קורה אילו Count היה מוגדר ב-classVariableNames: של Dog? אזי היה קיים תא אחד משותף בלבד ב-classPool של Dog, ולאחר 2 כלבים וצבוע אחד גם Dog count וגם Hyena count היו מחזירים 3! 
"מימוש classVarNames ו-allClassVarNames במחלקות הליבה:"
Behavior >> classVarNames
    ^Set new   "ברירת מחדל ב-Behavior (עבור מחלקות ללא classPool)"

Class >> classVarNames
    classPool isNil ifTrue: [ ^Set new ].
    ^classPool keys

Behavior >> allClassVarNames
    ^superclass isNil
        ifTrue: [ self classVarNames ]
        ifFalse: [ (superclass allClassVarNames) addAll: self classVarNames; yourself ]

Metaclass >> allClassVarNames
    ^theNonMetaClass allClassVarNames   "מטה-מחלקה מחזירה את משתני המחלקה של המחלקה שלה (thisClass)!"

9.5 סגירת המעגל הרפלקטיבי (Rules 8–10), מחלקות הליבה ו-5 סוגי המשתנים

חוקים 8–10, תפקידי Behavior, ClassDescription, Class ו-Metaclass, וחמשת סוגי המשתנים ב-Smalltalk.

1. חוקים 8, 9 ו-10 וארבע מחלקות הליבה

חיבור עץ המטה-מחלקות אל Class וסגירת המעגל ב-Metaclass:

  • Rule 8 (ירושה מ-Class ו-Behavior): שורש עץ המטה-מחלקות (ProtoObject class ב-Squeak) יורש מ-Class → ClassDescription → Behavior → Object → ProtoObject.
  • Rule 9 (מופעים של Metaclass): כל המטה-מחלקות הן מופעים של המחלקה Metaclass (אשר יורשת מ-ClassDescription, כאחות של Class).
  • Rule 10 (סגירת המעגל): המטה-מחלקה של Metaclass היא Metaclass class, והיא בעצמה מופע של Metaclass!
  • חלוקת אחריות בין 4 מחלקות הליבה:
    • Behavior: superclass, methodDict, format, הידור מתודות ויצירת מופעים (new, basicNew).
    • ClassDescription: משותפת ל-Class ול-Metaclass — שמות משתני מופע (instVarNames, addInstVarName:), פרוטוקולים, Change Sets ו-fileOut. (מיזוג Class לתוכה יכפה שדות של מחלקות בעלות שם על מטה-מחלקות אנונימיות!).
    • Class: שם גלובלי (name), מילון משתני מחלקה (classPool), מאגרים (sharedPools) ו-subclasses.
    • Metaclass: מצביע ליחידן thisClass ודריסת new האוכפת מופע יחיד בלבד לכל מטה-מחלקה.

2. חמשת סוגי המשתנים ב-Smalltalk

הבחנה מלאה לפי אות ראשונה, מספר עותקים בזיכרון וטווח הכרה:

  1. משתנה מופע (אות קטנה, ב-instanceVariableNames: של המחלקה): עותק נפרד לכל מופע; נגיש רק ממתודות מופע.
  2. משתנה מופע של מטה-מחלקה (אות קטנה, ב-Dog class instanceVariableNames: 'count'): עותק נפרד לכל מחלקה בעץ הירושה (עותק ל-Dog ועותק נפרד ל-Hyena!); נגיש רק ממתודות מחלקה.
  3. משתנה מחלקה (אות גדולה, ב-classVariableNames:): עותק אחד משותף למחלקה, למטה-מחלקה, לתתי-המחלקות ולכל מופעיהן!
  4. משתנה מאגר משותף (אות גדולה, ב-poolDictionaries:): משותף למחלקות שהצהירו על המאגר.
  5. משתנה גלובלי (אות גדולה, במילון Smalltalk): מוכר מכל מקום במערכת. (משתנה משותף לכל המטה-מחלקות מוגדר ב-classVariableNames: של Class!).

ארבע תבניות החשיבה שפוטרות כל בעיית רפלקציה ומטה-מחלקות

1. זיהוי נקודות הקצה של המודל: השוויון x class class == x מתקיים רק עבור Metaclass (רמה 4) ו-Metaclass class (רמה 5); והקבלת הירושה x superclass class == x class superclass נשברת עבור ProtoObject ועבור כל מטה-מחלקה (רמות 3 ו-5)!

3. מידע ייחודי לכל מחלקה בעץ ההורשה: נשמר תמיד במשתנה מופע של מטה-מחלקה (כדי שתת-מחלקה לא תדרוס את נתוני מחלקת האב).
4. עקיפת Method Lookup רגיל: שליחת withArgs:executeMethod: או perform:withArguments:inSuperclass: מריצה מתודה ממחלקת-על על המקבל self מבלי להיכנס ללולאה אינסופית.

מודל 5 הרמות ונקודות קצה

יצרנו מחלקה חדשה MyObject, ובמטה-מחלקה שלה MyObject class הגדרנו שתי מתודות: 

MyObject class >> magicNumber: aCheck
    | a |
    a := 0.
    (aCheck class class = aCheck) ifTrue: [ a := a + 1 ].
    (aCheck superclass class = aCheck class superclass) ifFalse: [ a := a + 2 ].
    ^a

MyObject class >> mystery: value with: b
    | curr next counter |
    curr := value.
    counter := 1.
    [ next := curr.
      curr := next class.
      b value: curr ] whileFalse: [ counter := counter + 1 ].
    ^counter

• ב-magicNumber:: תנאי 1 מוסיף 1 רק עבור עצם שמקיים aCheck class class = aCheck (כלומר רק עבור Metaclass או Metaclass class!). תנאי 2 מוסיף 2 כאשר הקבלת הירושה (חוק 7) נשברת (כלומר עבור מטה-מחלקות ברמות 3 ו-5 שבהן Metaclass ~= ClassDescription, או עבור שורש הירושה ProtoObject שבו ProtoObject superclass הוא nil שמחלקתו UndefinedObject ~= Class!).

מלכודות שייכות וירושה

1. מה יחזיר כל אחד מארבעת הביטויים הבאים, ומיהן כל המחלקות במערכת המקיימות X isKindOf: X?

1. TranslucentColor isKindOf: (TranslucentColor superclass)
2. Metaclass isKindOf: (Metaclass superclass)
3. Object isKindOf: ProtoObject
4. ProtoObject isKindOf: Object
✅ פתרון מלא ומנומק (לחצו לפתיחה) ▼

חלק 1 – ניתוח 4 ביטויי isKindOf: ו-5 המחלקות הדואליות:
המתודה X isKindOf: Y בודקת האם המחלקה של X (X class) שווה ל-Y או יורשת מ-Y:
• ביטוי 1 (TranslucentColor isKindOf: Color) ⬅ false! המחלקה של TranslucentColor היא TranslucentColor class, ששרשרת הירושה שלה היא TranslucentColor class → Color class → Object class → ProtoObject class → Class → ClassDescription → Behavior → Object → ProtoObject. המחלקה Color אינה מופיעה בשרשרת זו!
• ביטוי 2 (Metaclass isKindOf: ClassDescription) ⬅ true! המחלקה של Metaclass היא Metaclass class, שיורשת מ-ProtoObject class → Class → ClassDescription!
• ביטויים 3 ו-4 (Object isKindOf: ProtoObject ו-ProtoObject isKindOf: Object) ⬅ שניהם true! כי גם Object class וגם ProtoObject class יורשות מ-Class → ClassDescription → Behavior → Object → ProtoObject!
• 5 המחלקות היחידות שמקיימות X isKindOf: X (וכן (A isKindOf: B) and: [B isKindOf: A] לכל זוג מהן): אלו בדיוק 5 המחלקות שדרכן עוברת שרשרת הירושה של כל מטה-מחלקה החל מ-Class ומעלה: Class, ClassDescription, Behavior, Object, ProtoObject! (ו-Metaclass אינה ביניהן כי Metaclass היא אחות של Class!).

חלק 2 – מעקב Class hasMethods מול Class class hasMethods:
• בהרצת Class hasMethods: המקבל self הוא Class. החיפוש מתחיל ב-Class class ומטפס: Class class → ClassDescription class → Behavior class → Object class → ProtoObject class → Class, ומוצא את Class >> hasMethods! בתוכה: (א) super hasMethods מחפש מ-ClassDescription → Behavior >> hasMethods ובודק Class methodDict size > 0 (true); (ב) self class hasMethods שולח Class class hasMethods.
• בהרצת Class class hasMethods: המקבל self הוא המטה-מחלקה Class class, שמחלקתה היא Metaclass! החיפוש מתחיל ב-Metaclass → ClassDescription → Behavior! מכיוון ש-Metaclass אינה יורשת מ-Class, החיפוש מדלג לחלוטין על Class >> hasMethods ומפעיל ישירות את Behavior >> hasMethods שבודק (Class class) methodDict size > 0 ומחזיר true ללא רקורסיה אינסופית!

כתיבת מתודות רפלקטיביות

א. נגדיר "עומק של מחלקה" (classDepth) כמספר צעדי ההורשה מהמחלקה עד לשורש עץ ההורשה באותה רמה (עומק ProtoObject ברמה 2 הוא 0, ועומק ProtoObject class ברמה 3 הוא 0; עבור מופע ברמה 1 עומקו מוגדר כעומק מחלקתו). ממשו את classDepth, את objectModelLevel (המחזירה 1 עד 5), ואת depthAtLevel (המחזירה depth @ level, או ב-rankAndDepth מספר עשרוני depth + (level / 10.0)).
ב. ממשו ב-Behavior את freshMethods (מתודות חדשות שאינן דורסות), overiddenMethods (מתודות דורסות), ו-isCousinOf: aClass (שתי מחלקות שיש להן אב-קדמון משותף שאינו Object ואינו ProtoObject, ואף אחת אינה אב-קדמון של השנייה).

"א. שורש עץ ההורשה באותה רמה (classBase), עומק (classDepth) ומעמד (objectModelLevel):"
Behavior >> classBase
    ^ProtoObject         "שורש המחלקות הרגילות (רמה 2) ו-Metaclass (רמה 4)"

Metaclass >> classBase
    ^ProtoObject class   "שורש עץ המטה-מחלקות (רמות 3 ו-5)"

Behavior >> classDepth
    self = self classBase ifTrue: [ ^0 ].
    ^self superclass classDepth + 1

Object >> objectModelLevel
    self == Metaclass class ifTrue: [ ^5 ].
    self == Metaclass ifTrue: [ ^4 ].
    self isMetaclass ifTrue: [ ^3 ].
    self isBehavior ifTrue: [ ^2 ].
    ^1

Object >> depthAtLevel
    | lvl depth |
    lvl := self objectModelLevel.
    depth := self isBehavior ifTrue: [ self classDepth ] ifFalse: [ self class classDepth ].
    ^depth @ lvl   "וב-rankAndDepth מחזירים: ^(depth + (lvl / 10)) asFloat"

Behavior >> freshMethods

    ^self selectors reject: [ :sel | superclass canUnderstand: sel ]

MyClass class >> defaultValueFor: varNameString
