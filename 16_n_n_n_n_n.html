2. האתגר התכנותי בהכללה: איפה קובע המספר 8 באופן קשיח (Hard-coded)?

איתור שתי נקודות הקיבוע בפתרון של פרק 15 ב-Board>>initialize וב-Queen>>advance

כשאנחנו חוזרים אל הקוד שכתבנו בפרק 15 עבור 8 מלכות ושואלים את עצמנו: "מה בעצם מונע מהקוד שלנו לפתור לוח בגודל 5×5 או 10×10?", אנחנו מגלים שבפתרון של פרק 15 קובעו ערכים קשיחים (Hard-coded) של הספרה 8 בשני מקומות קריטיים:

מוקד קשיח 1 · יצירת שרשרת המלכות

בלולאת יצירת המלכות ב-Board>>initialize

הלוח יצר תמיד בדיוק 8 מלכות באמצעות הלולאה הקשיחה (1 to: 8) do: [...].

Board >> initialize
    lastQueen := QueenTerminator new.
    (1 to: 8) do: [:i |
        lastQueen := Queen new setColumn: i neighbor: lastQueen]
מוקד קשיח 2 · בדיקת קצה הלוח

בבדיקת גבול הלוח ב-Queen>>advance

כל מלכה בדקה האם הגיעה לשורה האחרונה באמצעות התנאי הקשיח row = 8 ifTrue: [...].

Queen >> advance
    row = 8 ifTrue: [
        neighbor nextSolution ifFalse: [^ false].
        row := 0].
    row := row + 1.
    ^ true

הגשר הנרטיבי: רגע, איך שומרים את הפרמטר N כך שגם הלוח וגם כל המלכות יכירו אותו?

להגדיר את גודל הלוח N כמשתנה מחלקה זה כמו לתלות שלט אחד ויחיד בכניסה לבניין שכתוב עליו "מספר החדרים בכל דירה". ברגע שדייר בדירה של חדר אחד מעדכן את השלט ל-1, גם דירת ה-5 חדרים בטוחה שיש לה רק חדר אחד!

משתנה מחלקה (classVariableNames) הוא עותק יחיד המשותף לכל המופעים של אותה המחלקה! כל אתחול של לוח חדש דורס את הערך של הלוחות הקודמים שנוצרו לפניו.

🎯 תובנת המפתח

כדי לאפשר קיומם של מספר לוחות בגדלים שונים בו-זמנית, חל איסור להשתמש במשתנה מחלקה: יש להגדיר את boardSize (או n) כמשתנה מופע ולהעבירו לכל מלכה כמשתנה מופע פרטי משלה (או כקישור למופע הלוח שלה).

1. ההצעה המפתה להכללת הלוח ל-N × N באמצעות משתנה מחלקה

בחינת הקוד המוצע שבו N מוגדר ב-classVariableNames של המחלקה Board

בוא נבחן יחד הצעה נפוצה מאוד להכללת בעיית המלכות ללוח בגודל N × N. מי שכתב את ההצעה הזו אמר לעצמו: "כדי שלא אצטרך לשנות את חתימת האתחול של כל מלכה ולהעביר לה את גודל הלוח, אשמור את N כמשתנה מחלקה ב-Board, ואכתוב מתודת מחלקה Board class >> N שכל מלכה תוכל לקרוא לה מתוך advance!"

הנה הקוד המוצע במלואו — קרא אותו בעיון:

⚠️ הקוד המוצע לבחינה (שימוש במשתנה מחלקה N):
Object subclass: #Board
    instanceVariableNames: 'lastQueen'
    classVariableNames: 'N'
    poolDictionaries: ''
    category: 'OOD-NQueens'

Board >> initialize: queensNum
    N := queensNum.
    lastQueen := QueenTerminator new.
    (1 to: N) do: [:i |
        lastQueen := Queen new setColumn: i neighbor: lastQueen]

Board class >> N
    ^ N

Queen >> advance
    row = Board N
        ifTrue: [
            neighbor nextSolution ifFalse: [^ false].
            row := 0].
    row := row + 1.
    ^ true

2. ניתוח הכשל והתוצאה המפתיעה בחלון ה-Workspace

למה לוח בגודל 5×5 (שיש לו 10 פתרונות חוקיים!) מחזיר פתאום No solution.!?

אם נבדוק את הקוד המוצע על לוח בודד בלבד, נדמה שהכל עובד מצוין. אבל תכנות מונחה עצמים נבחן בעולם שבו מספר מופעים חיים ופועלים במקביל! בוא נבחן מה מתרחש כאשר מריצים את חמש השורות הבאות בחלון ה-Workspace:

הקוד המורץ בחלון ה-Workspace:
board1 := Board new.
board2 := Board new.
board1 initialize: 5.
board2 initialize: 1.
board1 solve.
הפלט המתקבל בחלון ה-Transcript:
No solution.!

למרות שללוח בגודל 5×5 יש פתרונות חוקיים רבים, המערכת מדפיסה No solution.! — מדוע?!

בוא נפרק יחד, צעד אחר צעד, את ארבעת שלבי הכשל המבני שגרמו לתוצאה הזו:

1. משתנה מחלקה הוא עותק יחיד משותף

המשתנה N הוגדר כמשתנה מחלקה (classVariableNames: 'N'). כפי שלמדנו בעקרונות השפה, משתנה מחלקה הוא עותק יחיד המשותף לכל המופעים של אותה המחלקה.

2. אתחול הלוח הראשון (board1 initialize: 5)

כאשר נוצר ואותחל הלוח הראשון (board1 initialize: 5), ערכו של משתנה המחלקה N נקבע ל-5, ונוצרה ב-board1 שרשרת של 5 מלכות.

3. הדריסה הקטלנית (board2 initialize: 1)

מיד לאחר מכן, כאשר אותחל הלוח השני (board2 initialize: 1), הוא ניגש לאותו משתנה מחלקה משותף N, דרס את ערכו הקודם ושינה אותו מ-5 ל-1!

4. קריסת החיפוש ב-board1 solve

כאשר מופעלת המתודה board1 solve, 5 המלכות של הלוח הראשון פונות במתודה advance אל Board N ומקבלות כולן את הערך המעודכן: 1! לכן ברגע שמלכה מגיעה לשורה 1 היא מניחה שהגיעה לקצה הלוח ונסוגה — ואי אפשר להציב 5 מלכות בשורה אחת בלבד!

3. הפתרון התקני מונחה העצמים: משתני מופע פרטיים לכל לוח ולכל מלכה

איך מאפשרים למספר לוחות בגדלים שונים להתקיים ולפעול בו-זמנית ללא התנגשות?

✅ כללי הפתרון התקני מונחה העצמים:

  • כדי לאפשר קיומם של מספר לוחות בגדלים שונים בו-זמנית, חל איסור להשתמש במשתנה מחלקה משותף עבור גודל הלוח.
  • במקום זאת, יש להגדיר את boardSize (או n) כמשתנה מופע (instanceVariableNames) של המחלקה Board.
  • בעת יצירת המלכות, גודל הלוח מועבר לכל מלכה כמשתנה מופע פרטי משלה (למשל במתודת אתחול מורחבת setColumn:neighbor:boardSize:), או לחלופין כל מלכה מחזיקה קישור למופע הלוח שלה.

שאלה 2 (רמת הבנה): מדוע בקוד של איור 16.1 אנו מפעילים את ההודעה abs בעת חישוב המשתנים dx, dy ו-dz? ▼
🎯 הדילמה: אלכסון יכול לעלות או לרדת בכל ציר (הפרש חיובי או שלילי) — איך בודקים את כל כיווני האלכסונים בנוסחה אחת פשוטה?

🎯 שורה תחתונה: השימוש ב-abs מאחד את כל כיווני האלכסונים לבדיקת שוויון מרחקים פשוטה ונקייה.

💡 ההסבר האינטואיטיבי שלי: ארבעת התנאים באיור 16.1 מכסים את כל מצבי האיום האפשריים בין מלכות במפלסים שונים:
1. ((dx = 0) and: [ dy = 0 ]) ifTrue: [ ^ true ]: שתי המלכות חולקות את אותה שורה ואותה עמודה — הן נמצאות זו מעל זו באותו עמוד אנכי.
2. ((dx = 0) and: [ dy = dz ]) ifTrue: [ ^ true ]: המלכות נמצאות באותה שורה (dx = 0) ועל אלכסון במישור עמודה-מפלס (dy = dz).
3. ((dx = dz) and: [ dy = 0 ]) ifTrue: [ ^ true ]: המלכות נמצאות באותה עמודה (dy = 0) ועל אלכסון במישור שורה-מפלס (dx = dz).
4. ((dx = dy) and: [ dx = dz ]) ifTrue: [ ^ true ]: המלכות נמצאות על אלכסון מרחבי תלת-ממדי מלא שבו כל שלושת ההפרשים שווים (dx = dy = dz).

🎯 שורה תחתונה: שלושת התנאים הראשונים בודקים איום במישורים המאונכים לשורות/לעמודות, והתנאי הרביעי בודק את האלכסון הראשי של הקובייה התלת-ממדית.
שאלה 4 (רמת ניתוח): נתונות שתי מלכות במרחב: Q1(2, 5, 1) ו-Q2(2, 2, 4). עקוב אחר הקוד באיור 16.1 וקבע מהם ערכי dx, dy, dz ואיזו שורת תנאי תחזיר true. ▼

• dy := (2 - 5) abs ← 3
• dz := (4 - 1) abs ← 3

• תנאי 1: (dx = 0) and: [ dy = 0 ] ← false (כי dy = 3).
• תנאי 2: (dx = 0) and: [ dy = dz ] ← מתקיים! (כי dx = 0 וגם 3 = 3). לכן שורה זו מחזירה מיד ^ true (איום באלכסון במישור עמודה-מפלס).
