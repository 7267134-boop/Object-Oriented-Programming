1. מעמדה הארכיטקטוני של המחלקה Object ומקומה של ProtoObject

מדוע כמעט כל מחלקה יורשת מ-Object, למה נוספה מעליה ProtoObject, ולמה אסור להוסיף לה שדות?

אנחנו נכנסים עכשיו אל לב ליבה של ספריית המחלקות בסביבת Squeak. אם בפרקים הקודמים למדנו איך לבנות מחלקות ואיך עובד מנגנון הירושה, עכשיו אני רוצה שנפתח את מכסה המנוע של השפה עצמה ונכיר מקרוב את עמודי התווך שעליהם בנוי כל עולם ה-Smalltalk.

בראש הפירמידה הזו ניצבת המחלקה Object. חשוב לנו מאוד להכיר את המתודות של Object, משום שרוב רובן המוחלט של המחלקות בסביבת Squeak יורשות ממנה — בין אם ישירות ובין אם בעקיפין. לכן, Object היא זו שמגדירה את התשתית ואת ההתנהגות הבסיסית והמשותפת של כלל העצמים במערכת.

אגב, אם תסתכל על הקצה העליון ביותר של עץ הירושה בסביבת העבודה Squeak, תגלה שמעל Object נוספה מחלקת-על רזה ומינימלית בשם ProtoObject (שממנה יורשת Object). תפקידה של ProtoObject הוא לרכז אך ורק את ההגדרות הגרעיניות ביותר של עצמים — כמו בדיקת זהות פרימיטיבית בזיכרון (==), בדיקת isNil ומתודת האתחול initialize — עבור עצמים מיוחדים ונדירים (כגון עטיפות Proxy) שאינם מעוניינים לרשת את כל המטען העשיר של Object.

🚫 החלטה הנדסית קריטית: איסור הוספת משתני מופע ל-Object!

למופעים של Object אין משתני מופע כלל, וחל איסור מוחלט להוסיף לה משתני מופע! מדוע? מכיוון שכל מחלקה במערכת יורשת מ-Object, הוספת משתנה מופע ל-Object תשנה מיידית את המבנה הפיזי בזיכרון של כל העצמים והמחלקות במערכת! שינוי מבנה כזה הוא הרה אסון עבור מחלקות קריטיות (כגון SmallInteger), אשר המכונה הווירטואלית (VM) מסתמכת על המבנה והייצוג הפיזי המדויק שלהן לצורך ביצועים.

🧭 כ-400 מתודות ב-Object: שני סוגי התנהגויות

  • 1. התנהגות משותפת (Common Behavior): מתודות גנריות המספקות שירות שלם ואין שום צורך או סיבה לדרוס אותן בתת-מחלקות (למשל printString, ~~, ~=).
  • 2. התנהגות ברירת מחדל (Default Behavior): מתודות בסיסיות שנועדו לכך שתת-מחלקות ידרסו אותן (Overriding) ויספקו מימוש מותאם וייחודי עבורן (למשל printOn:, =).

2. מתודות הדפסה (printString ו-printOn:) ועצמים המשערכים את עצמם

איך תבנית Template Method מפרידה בין יצירת הזרם לבין כתיבת התוכן, ולמה קיים רווח ב-Point עם y שלילי?

איך עצם ב-Smalltalk יודע להפוך את עצמו למחרוזת טקסט קריאה כשאנחנו מדפיסים אותו? הדפסת עצם מתבצעת באמצעות שליחת ההודעה printString אל העצם. למעשה, כאשר אתה מסמן ביטוי בחלון העבודה (Workspace) ומבקש להדפיס אותו (באמצעות ctrl+p / print it), המערכת מעריכה תחילה את הביטוי כולו, ואז שולחת אוטומטית את ההודעה printString אל העצם המוחזר — ולכן אין צורך להקיף ביטויים בסוגריים בחלון העבודה רק כדי להדפיס אותם!

אבל כאן מסתתר עיצוב הנדסי מבריק: המתודה printString היא התנהגות משותפת שאנחנו לא דורסים. מאחורי הקלעים היא שולחת לעצם את ההודעה self printStringLimitedTo: 50000, אשר יוצרת זרם תווים / זרם פלט (WriteStream) ושולחת אל העצם את ההודעה printOn: aStream עם הזרם כארגומנט! המתודה printOn: היא כבר התנהגות ברירת מחדל שאמורה לכתוב אל הזרם aStream סדרת תווים המייצגת את העצם. בוא נראה איך Object מממשת אותה כברירת מחדל:

Object >> printOn: aStream
    "Append to the argument, aStream, a sequence of characters that identifies the receiver."
    | title |
    title := self class name.
    aStream
        nextPutAll: (title first isVowel ifTrue: ['an '] ifFalse: ['a ']);
        nextPutAll: title

בוא נעקוב יחד אחרי הקוד של Object >> printOn:: המתודה שולפת את שם המחלקה של העצם ושומרת אותו במשתנה המקומי title (באמצעות self class name). לאחר מכן היא בודקת האם התו הראשון בשם המחלקה הוא אות תנועה באנגלית או עיצור (title first isVowel), וכותבת לזרם את התווית הדקדוקית המתאימה — 'an ' או 'a ' — ואחריה את שם המחלקה עצמו (למשל 'a Point' או 'an Object'). שים לב שפעולת הכתיבה לזרם מתבצעת באמצעות ההודעה nextPutAll:, אשר מקבלת אוסף כלשהו (כגון מחרוזת או מערך), עוברת על איברי האוסף ומשרשרת אותם בזה אחר זה אל תוך הזרם!

הגדרה מחדש (Overriding) של printOn: במחלקה Point: תודות למנגנון הירושה, כל עצם מבין את printOn:, אך במחלקות המייצגות ערכים אנו דורסים אותה כדי להעניק לעצם ייצוג שימושי ומשמעותי יותר מאשר סתם 'a Point'. הנה המימוש במחלקה Point (בעלת משתני המופע x ו-y המייצגים מיקום במישור):

Point >> printOn: aStream
    "The receiver prints on aStream in terms of infix notation."
    x printOn: aStream.
    aStream nextPut: $@.
    (y isNumber and: [y negative]) ifTrue: [aStream space].
    y printOn: aStream

🔍 למה נוספה שורת הרווח עבור y שלילי ב-Point?

המתודה שולחת printOn: aStream אל x, משרשרת את התו הבודד $@ באמצעות nextPut: $@, ואז מדפיסה את y (כך שעבור הנקודה 3@4 מודפסת המחרוזת '3@4').
אבל למה בודקים (y isNumber and: [y negative]) ifTrue: [aStream space]? אם y הוא מספר שלילי (למשל -4), ללא הרווח היה מודפס הביטוי 3@-4, שב-Smalltalk מתפרש כאופרטור בינארי בלתי חוקי בשם @- ואינו ניתן לפענוח תחבירי תקין של נקודה! הוספת הרווח יוצרת את הפלט 3@ -4, המאפשר פענוח וקריאה מחדש של הטקסט כקוד Smalltalk תקני!

💡 עצמים המשערכים את עצמם (Self-Evaluating Objects)

עצם נקרא Self-Evaluating (או Evaluating Self) כאשר ערכו זהה לעצמו — כלומר תוצאת ה-printString שלו (כשמדפיסים אותו עם ctrl+p) מהווה קוד Smalltalk תקני שהרצתו (ב-do it או print it) מחזירה עצם בעל ערך זהה!
• דוגמאות: מספרים, תווים, סימבולים, נקודות (Point), תחומים (Interval), ומערכים סטטיים (#(...)).
• מערכים דינמיים ({...}): הם self-evaluating רק כאשר כל איבריהם הם self-evaluating! למשל, ביצוע {3@4. 4.5} מחזיר {3@4 . 4.5} (הוא כן self-evaluating), אך ביצוע {3@4. 4+5} מחזיר {3@4 . 9} (הוא אינו זהה לקוד המקור 4+5 שיצר אותו!).

3. זהות (==, ~~) מול שוויון (=, ~=) וחוזה ה-hash

ההבדל בין כתובת זיכרון לתוכן מבני, תפקיד ההודעה species ב-Point, וחוק הברזל של דריסת hash

אחת האבחנות החשובות ביותר בתכנות מונחה עצמים היא ההבדל בין השאלה "האם שני מצביעים מתייחסים בדיוק לאותו עצם פיזי בזיכרון?" (זהות – Identity) לבין השאלה "האם שני עצמים מייצגים את אותו ערך ותוכן?" (שוויון – Equality):

📍 בדיקת זהות פיזית (== ו-~~)

  • == (זהות): ממומשת במחלקת ProtoObject כפרימיטיב המשווה ישירות כתובות זיכרון ומצביעים (האם שני הביטויים מתייחסים לאותו עצם עצמו).
  • ~~ (אי-זהות): ממומשת כהתנהגות משותפת: anObject == self ifTrue: [^false] ifFalse: [^true]

⚖️ בדיקת שוויון ערכי (= ו-~=)

  • = ב-Object (ברירת מחדל): מוגדרת כבדיקת זהות: ^self == anObject. מחלקות המייצגות ערכים דורסות אותה לשוויון מבני.
  • ~= (אי-שוויון): ממומשת ב-Object כ- ^(self = anObject) not — לכן דריסה של = מעדכנת אוטומטית גם את תוצאת ~= ואין סיבה לדרוס את ~=!

בוא נראה כיצד המחלקה Point דורסת את מתודת השוויון = כך שהנקודה (3@4) תהיה שווה לנקודה (3@4) גם כאשר מדובר בשני עצמים נפרדים בזיכרון:

Point >> = aPoint
    self species = aPoint species
        ifTrue: [^x = aPoint x and: [y = aPoint y]]
        ifFalse: [^false]

המתודה מוודאת תחילה ששני העצמים שייכים לאותו ה-species (אותה משפחת טיפוסים לוגית), ורק אם כן — היא בודקת שוויון ערכים בין קואורדינטות ה-x ובין קואורדינטות ה-y.

🔑 חוק בל יעבור ב-OOP: הקשר החיוני בין = לבין מתודת hash!

ההודעה hash המוגדרת ב-Object מחזירה מספר שלם המאפיין ומייצג את העצם לצורך אחסון וחיפוש מהיר כמפתחות במילונים (Dictionary) ובקבוצות (Set).
כלל הברזל הארכיטקטוני קובע: אם דרסת את מתודת השוויון =, חובה עליך לדרוס בהתאמה גם את מתודת ה-hash, כך ששני עצמים שנקבע כי הם שווים (a = b) יחזירו תמיד את אותו ערך hash מדויק (a hash = b hash)! אם תפר את החוזה הזה, מילונים וקבוצות יחפשו את העצם בתא הלא נכון ולא יצליחו למצוא אותו!

1. רפלקציה ושייכות למחלקה (Class Membership) בזמן ריצה

המתודות class, isMemberOf:, isKindOf: ו-respondsTo: — ומדוע שימוש יתר בהן נחשב ל-Anti-Pattern?

בזכות העובדה שב-Smalltalk גם המחלקות עצמן הן אובייקטים חיים, המחלקה Object מעניקה לנו סט של מתודות שמאפשרות לתשאל כל עצם בזמן ריצה לגבי המחלקה שלו והיכולות שלו:

1. class

מחזירה את עצם המחלקה הישירה של המקבל.
• לדוגמה: הביטוי 4 class מחזיר את עצם המחלקה SmallInteger, והביטוי (3@4) class מחזיר את עצם המחלקה Point.

2. isMemberOf: aClass

מקבלת מחלקה כפרמטר ומחזירה true אך ורק אם המקבל הוא מופע מדויק וישיר של aClass!
• לדוגמה: 4 isMemberOf: SmallInteger מחזיר true, ואילו 4 isMemberOf: Number מחזיר false (למרות ש-SmallInteger היא תת-מחלקה של Number!).

3. isKindOf: aClass

מקבלת מחלקה כפרמטר ומחזירה true אם המקבל הוא מופע של aClass או של כל תת-מחלקה שלה במעלה עץ הירושה.
• לדוגמה: 4 isKindOf: SmallInteger, 4 isKindOf: Number ו-4 isKindOf: Object מחזירים שלושתם true, אך 4 isKindOf: Point מחזיר false.

4. respondsTo: aSymbol

מקבלת סלקטור (שם של הודעה) כסימבול (עם קידומת סולמית #) ומחזירה true אם העצם כולל מתודה מתאימה ומבין את ההודעה.
• לדוגמה: 4 respondsTo: #+ ו-'hello' respondsTo: #size מחזירים שניהם true.

⚠️ כלל הנדסי חשוב (מדוע זהו Anti-Pattern?): באופן כללי, בתכנות מונחה עצמים טהור לא מומלץ לבדוק במפורש את סוג העצם (isKindOf:, isMemberOf:) או אם הוא מבין הודעה כלשהי (respondsTo:) בקוד הרגיל שלנו! בדיקות כאלו פוגעות בגמישות ובפולימורפיזם; במקום זאת, עדיף לשלוח את ההודעה ישירות ולסמוך על מנגנון הקישור הדינמי שיאתר את המתודה המתאימה במעלה היררכיית הירושה.

2. העתקה ושכפול עצמים (shallowCopy, copyTwoLevel, deepCopy, copy + postCopy)

מדוע משתני מופע כמצביעים יוצרים שיתוף זיכרון מסוכן בשכפול רדוד, ואיך דריסת postCopy פותרת זאת באלגנטיות?

כשאנחנו משכפלים עצם, אנחנו רוצים בדרך כלל לקבל עצם חדש ועצמאי שהמבנה וההתנהגות שלו זהים לאלה של העצם המקורי, מבלי שהעותק החדש והעצם המקורי ישתפו ביניהם מידע פנימי שעלול להשתנות (למשל, אם נשכפל נקודה Point, לא נרצה ששינוי ב-x של העותק ישנה גם את הנקודה המקורית). אלא שבשפת Smalltalk כל משתני המופע ממומשים כמצביעים לזיכרון (Pointers)! לכן המחלקה Object מציעה מספר רמות שכפול:

1. שכפול רדוד – shallowCopy (מבוסס על basicSize ו-basicAt:)

שיתוף מצביעים פנימיים!

המתודה shallowCopy (הממומשת על בסיס המתודות הפרימיטיביות basicSize ו-basicAt:) משכפלת את עצם השורש בלבד; כל משתני המופע הפנימיים שלו מועתקים כמצביעים זהותיים ומשותפים בין העותק למקור! בוא נראה דוגמה מוחשית עם מערך דו-ממדי:

a1 := {{'a'. 'b'}. {'c'. 'd'}}.
a2 := a1 shallowCopy.
(a1 at: 1) at: 1 put: 'z'.

אם נבדוק כעת את a2, נגלה שגם בו האיבר הראשון הפך ל-'z' (כלומר {{'z'. 'b'}. {'c'. 'd'}}), משום שתתי-המערכים ברמה הראשונה משותפים זהותית בין a1 ל-a2!

2. copyTwoLevel

משכפלת את השורש ומשכפלת רדודה כל אחד מהאיברים ברמה הראשונה (רמה אחת נוספת פנימה). בדוגמה הדו-ממדית שלנו שינוי ב-a1 לא ישפיע על a2; אך אם נגדיר מערך עם שלוש רמות קינון (a1 := {{{'a'}. {'b'}}. {{'c'}. {'d'}}}), השכפול של הרמה השלישית יישאר משותף!

3. deepCopy

מבצעת שכפול עמוק ורקורסיבי מלא של כל גרף/עץ העצמים בכל רמות העומק ככל הנדרש, כך שנוצר עותק עצמאי לחלוטין.

4. copy + postCopy (הגישה התקנית!)

המתודה copy ב-Object ממומשת כך: copy ^ self shallowCopy postCopy ברירת המחדל של postCopy מחזירה את self. תת-מחלקות נדרשות לדרוס אך ורק את postCopy ולשכפל בה ספציפית שדות שאסור שיהיו משותפים!

3. ניפוי שגיאות ומצבים חריגים (error handling), בדיקות ואתחול (initialize)

המתודות halt, assert:, deprecated:, doesNotUnderstand:, error:, subclassResponsibility, shouldNotImplement ו-initialize

בפרוטוקול error handling במחלקה Object מוגדר אוסף עשיר של מתודות תשתית לניפוי שגיאות, לתכנון לפי חוזה ולטיפול במצבים חריגים:

• halt

משמשת לניפוי שגיאות: שליחת ההודעה (למשל self halt מתוך מתודה) משהה את ביצוע התוכנית ומקפיצה מיידית את חלון ה-Debugger על מחסנית הקריאות הפעילה לבחינת ערכי המשתנים בזמן אמת.

• assert: aBlockOrBoolean

תומכת במודל Design by Contract (תכנון לפי חוזה) להגדרת תנאי כניסה ויציאה למתודות. מקבלת בלוק או ערך בוליאני, ואם התנאי אינו מתקיים (false) – מפסיקה את הביצוע, מעוררת חריגת AssertionFailure ופותחת את ה-Debugger.

• deprecated: anExplanationString

מתריעה למתכנת שהמתודה מיושנת ומציעה חלופה קיימת. למשל, המתודה הישנה doIfNotNil: ב-Object הוחלפה ב-ifNotNilDo: ומשוכתבת עם הודעת deprecated: לפני קריאה למתודה החדשה.

• doesNotUnderstand: aMessage

מתודת הגיבוי של הקישור הדינמי! כאשר חיפוש מתודה נכשל במעלה עץ הירושה, ההודעה doesNotUnderstand: נשלחת לעצם כהזדמנות אחרונה לטיפול בשגיאה (או לבניית Proxy דינמי) לפני קריסה ב-Debugger.

• error: aString / error

מעוררת באופן יזום מצב חריג (Exception) עם הודעת שגיאה מותאמת.

• subclassResponsibility מול shouldNotImplement

subclassResponsibility: מגדירה מתודות מופשטות (Abstract Methods) ומעוררת חריגה המציינת שעל תת-המחלקה לממש את המתודה.
shouldNotImplement: משמשת כשמתודה שנורשה ממחלקת-על אינה מתאימה סמנטית לתת-המחלקה ("ביטול" מתודה מורשת) ומעוררת שגיאה שאין להשתמש בה בעצם זה.

🔍 בדיקות (Testing): isNil ו-notNil כיוצאות דופן

אף ש-Object כוללת מתודות בדיקה כגון isArray, isBoolean, isBlock, השימוש בהן אינו מומלץ משום שהוא מפר את עקרון הכימוס (Encapsulation) והפולימורפיזם (עדיף לשלוח הודעה לעצם ולתת לו לבחור את התגובה המתאימה). עם זאת, המתודה isNil (של ProtoObject) והמתודה notNil (של Object) הן יוצאות דופן ושימושיות מאוד לבדיקה האם משתנה או עצם מאותחלים!

🚀 אתחול עצמים: initialize ו-super initialize

המתודה initialize (המוגדרת ב-ProtoObject) אחראית לאתחול עצמים. בסביבת Squeak, מימוש ברירת המחדל של new שולח אוטומטית למופע החדש את ההודעה initialize מיד לאחר יצירתו! תת-מחלקות הדורסות את initialize כדי לאתחל את משתני המופע שלהן חייבות לפתוח תמיד בקריאה ל-super initialize כדי שמחלקות-העל יאתחלו כהלכה את משתני המופע שהוגדרו בהן.

1. היררכיית המספרים ב-Smalltalk והמחלקה המופשטת Magnitude

למה מספרים הם עצמים מלאים תחת הקטגוריה Kernel-Numbers, ואיך עובדת תבנית ה-Template Method ב-Magnitude?

בשפות תכנות כמו Java או C, התרגלנו להפרדה חדה: יש "אובייקטים", ויש "טיפוסים פרימיטיביים" (כמו int או float) שאינם אובייקטים. ב-Smalltalk התמונה טהורה ואחידה לחלוטין: המספרים הם עצמים מלאים לכל דבר ועניין, והם מאורגנים תחת הקטגוריה Kernel-Numbers. בוא נתבונן במבנה עץ הירושה שלהם:

Object
  └── Magnitude (Abstract: <, =, >, <=, >=, min:, max:, between:and:)
        └── Number (Abstract: +, -, *, /, //, \\, @, sqrt, squared, raisedTo:, sin, log, even, odd, positive, negative, asFloat, asInteger)
              ├── Integer (Abstract: factorial, gcd:, isPrime, atRandom)
              │     ├── SmallInteger
              │     ├── LargePositiveInteger
              │     └── LargeNegativeInteger
              ├── Float (e.g. pi, e)
              └── Fraction (numerator / denominator)

בוא נתחיל מהקומה הראשונה מתחת ל-Object: המחלקה המופשטת Magnitude. מחלקה זו מאגדת את כל הישויות במערכת הניתנות להשוואה ולסדר (לא רק מספרים, אלא גם תווים Character, תאריכים וזמנים!). איך היא עובדת? ב-Magnitude מוגדרות שתי מתודות מופשטות בלבד (באמצעות subclassResponsibility): < ו-=. וכל שאר מתודות ההשוואה — >, <=, >=, min:, max:, ו-between:and: — ממומשות ב-Magnitude באופן מלא על גבי < ו-= (זוהי דוגמה מופתית לתבנית העיצוב Template Method)!

2. המחלקה Number, חילוק שלמים (//, \\), SmallInteger ו-Fraction

המתודות המופשטות ב-Number, המימוש האלגנטי של שארית החלוקה \\, המרה שקופה בשלמים ושברים מצומצמים

מתחת ל-Magnitude נמצאת המחלקה המופשטת Number, המוסיפה את כל מנגנוני החישוב האריתמטיים:

➕ אופרטורים ופונקציות ב-Number

  • אופרטורים אריתמטיים בסיסיים: +, -, *, / מוגדרים ב-Number כמתודות מופשטות הנשענות על subclassResponsibility.
  • הודעת @: יוצרת מופע של נקודה (Point) — למשל 10 @ 20.
  • פונקציות מתמטיות מובנות: sqrt, squared, raisedTo:, sin, log (וב-Float קבועים כגון pi ו-e; וב-Integer פעולות כגון factorial, gcd:, isPrime, atRandom).
  • בדיקות והמרות: even, odd, positive, negative, וכן asFloat, asInteger.

➗ מנגנון החילוק והשארית בשלמים (// ו-\\)

בנוסף לחילוק הרגיל /, המחלקה Number מגדירה שני אופרטורים מיוחדים לחלוקת שלמים:
• // (חילוק שלמים): מבצע חילוק שלמים ומעגל את המנה תמיד כלפי מטה (לכיוון אינסוף שלילי).
• \\ (שארית החלוקה / מודולו): מחזיר את שארית החלוקה. תראה כמה אלגנטי המימוש שלו ב-Number שנשען על //:

Number >> \\ aNumber
    ^ self - (self // aNumber * aNumber)

🚀 SmallInteger והמרת טיפוסים אוטומטית ושקופה

המחלקה SmallInteger מייצגת מספרים שלמים בטווח קבוע המנוהל ישירות במכונה הווירטואלית (VM) ביעילות גבוהה (הוא נשמר באופן ישיר בזיכרון במקום להיות מצביע לעצם).
הקסם של Smalltalk: המתכנת לעולם לא צריך לבחור בין SmallInteger ל-LargeInteger! כאשר מתרחשת חריגה מגבולות הטווח (Overflow), המערכת מזהה זאת וממירה את המספר אוטומטית ושקופה ל-LargePositiveInteger או ל-LargeNegativeInteger ללא שום קטיעה וללא אובדן מידע!

🍰 המחלקה Fraction: שברים פשוטים ללא אובדן דיוק!

כאשר אנחנו מחלקים שני מספרים שלמים באמצעות / ותוצאת החילוק אינה שלמה, Smalltalk אינה מבצעת עיגול לאובדן מידע (אינה חותכת לשלם ואינה הופכת לנקודה צפה מקורבת), אלא יוצרת מופע של המחלקה Fraction!
עצם Fraction שומר על מונה (numerator) ומכנה (denominator) מדויקים, והוא תמיד נשמר בצורה המצומצמת ביותר — לדוגמה, הביטוי 6 / 8 יחזיר אוטומטית את השבר המצומצם (3/4)!

1. סעיף 11.3: תווים (Character) – יורשים ישירים של Magnitude

תחביר $, תווים לא דפיסים, Character value:, בדיקות תווים ומשתנה המחלקה CharacterTable

בוא נכיר תחילה את אבן הבניין הבודדת של כל טקסט: המחלקה Character. המחלקה Character מוגדרת תחת הקטגוריה Collections-Strings, אך מבחינת עץ הירושה היא יורשת ישירות מהמחלקה המופשטת Magnitude! המשמעות היא שניתן להשוות בין תווים ישירות באמצעות <, >, between:and: וכל שאר מתודות הסדר של Magnitude (למשל $a < $z מחזיר true).

1. יצירת תווים ליטרליים ולא-דפיסים
  • תווים ליטרליים: נרשמים באמצעות הסימן $ — למשל $a, $Z, $7.
  • תווים מיוחדים שאינם דפיסים: נוצרים באמצעות מתודות מחלקה ב-Character: Character space, Character cr, Character tab, Character backspace, Character escape, Character enter
2. קוד ASCII/Unicode ו-CharacterTable
  • Character value: anInteger: מתודת מחלקה המקבלת מספר שלם המייצג ערך קוד ASCII או Unicode ומחזירה את מופע התו המתאים (למשל Character value: 65 מחזיר $A).
  • משתנה המחלקה CharacterTable: מאחסן טבלת מופעים מוכנים מראש של תווי ה-ASCII.
3. מתודות בדיקה והמרה ב-Character
  • מתודות בדיקה: isDigit, isLetter, isAlphaNumeric, isLowercase, isUppercase, isVowel.
  • המרה למחרוזת: המתודה asString ממירה את התו הבודד למחרוזת באורך 1 (למשל $a asString מחזיר 'a').

2. סעיף 11.4: מחרוזות (ByteString) וסימבולים (Symbol)

היררכיית האוספים של String, ההבדל המהותי בין ByteString ל-Symbol, וכל מתודות הטיפול במחרוזות

בשונה מתו בודד, מחרוזת (String) היא אוסף סדור של תווים הנגישים לפי אינדקס. לכן המחלקה String אינה יורשת מ-Magnitude כענף נפרד של מספרים, אלא משתלבת בתוך עץ האוספים (Collection). בוא נראה את מקומה המדויק בהיררכיה:

Object
  └── Collection
        └── SequenceableCollection
              └── ArrayedCollection
                    ├── Array
                    ├── String (מופשטת)
                    │     ├── ByteString (קונקרטית - מחרוזת רגילה הניתנת לשינוי)
                    │     └── Symbol (ייחודית בזיכרון - Interned & Immutable)
                    └── Text

המחלקה String עצמה מוגדרת כמחלקה מופשטת. בפועל, כשאנחנו עובדים עם טקסט ב-Smalltalk, אנחנו עובדים עם שתי תת-המחלקות הקונקרטיות שלה — וההבדל ביניהן הוא אחד הנושאים החשובים ביותר בשפה:

📝 מחרוזת רגילה – ByteString

'hello'
  • תחביר: נרשמת בין גרשיים בודדים: 'hello'.
  • אינה ייחודית בזיכרון: ייתכנו שתי מחרוזות שונות בזיכרון בעלות תוכן זהה לחלוטין. לכן עבור שתי מחרוזות כאלו הביטוי s1 = s2 יחזיר true (שוויון תוכן), אך השוואת הזהות s1 == s2 תחזיר false (שני אובייקטים נפרדים בזיכרון).
  • ניתנת לשינוי (Mutable): ניתן לערוך ולעדכן את התווים שבתוכה במקום באמצעות s1 at: 1 put: $H.

💎 סימבול ייחודי – Symbol

#hello
  • תחביר: נפתח בסימן סולמית: #hello.
  • עצם ייחודי במערכת (Interned Object / Singleton פנימי): המערכת מבטיחה שלעולם לא יתקיימו שני סימבולים עם אותו תוכן כאובייקטים נפרדים. שתי מחרוזות סימבול בעלות אותם תווים מצביעות תמיד על אותו העצם בדיוק בזיכרון (s1 == s2 מחזיר תמיד true!).
  • בלתי ניתן לשינוי (Immutable): לא ניתן לשנות את תוכנו של סימבול לאחר יצירתו.
  • יתרון ביצועים אדיר: השוואת סימבולים מהירה להפליא, כי מספיק להשוות את מצביעי הזיכרון שלהם (זהות פיזית ==) במקום להשוות אות-אחר-אות!

1. פעולות גישה ועדכון

1. ארכיטקטורת Boolean, מופעים יחידים (Singletons) ותנאים ללא IF

איך פולימורפיזם טהור בין המחלקות True ו-False מייתר לחלוטין את הצורך במבני בקרה תחביריים?

הגענו אל אחת הפנינים היפות ביותר של שפת Smalltalk. בשפות כמו C, Java או Python, מילות המפתח if, else ו-switch הן חלק קשיח מתחביר השפה ומהמהדר. ב-Smalltalk אין מבני בקרה פרימיטיביים בשפה כלל! הכל — כולל תנאים והסתעפויות — מתנהל דרך העברת הודעות ופולימורפיזם טהור.

איך הקסם הזה בנוי? תחת המחלקה Object מוגדרת המחלקה המופשטת Boolean. למחלקה זו יש שתי תת-מחלקות קונקרטיות בלבד:

  • True: מייצגת אמת לוגית. קיים לה מופע יחיד בדיוק במערכת (Singleton), המיוצג על ידי המשתנה-פסאודו true.
  • False: מייצגת שקר לוגי. קיים לה מופע יחיד בדיוק במערכת (Singleton), המיוצג על ידי המשתנה-פסאודו false.

עכשיו תראה איך פועלות מתודות התנאי (ifTrue:ifFalse:, ifTrue:, ifFalse:, ifFalse:ifTrue:) שמקבלות בלוקים של קוד כארגומנטים: כאשר אנחנו כותבים (x > 0) ifTrue: [block1] ifFalse: [block2], הביטוי x > 0 מוערך ומחזיר או את העצם true (מופע של True) או את העצם false (מופע של False). ואז נשלחת אליו ההודעה ifTrue:ifFalse:!

True >> ifTrue: trueBlock ifFalse: falseBlock
    "מריצה את הבלוק הראשון ומתעלמת מהשני!"
    ^ trueBlock value

True >> not
    ^ false
False >> ifTrue: trueBlock ifFalse: falseBlock
    "מריצה את הבלוק השני ומתעלמת מהראשון!"
    ^ falseBlock value

False >> not
    ^ true

תעצור לרגע להתפעל מזה: במחלקה True, המתודה ifTrue:ifFalse: פשוט שולחת את ההודעה value לבלוק הראשון ומתעלמת לחלוטין מהבלוק השני — בלי שום בדיקת תנאי פנימית! ובמחלקה False, אותה מתודה בדיוק פשוט שולחת value לבלוק השני ומתעלמת מהראשון! באותו אופן בדיוק, המתודה not (שלילה) ממומשת ב-True על ידי החזרת הקבוע false, וב-False על ידי החזרת הקבוע true. זהו פולימורפיזם טהור בהתגלמותו!

2. אופרטורים לוגיים: הערכה מקוצרת (and:, or:) מול הערכה מלאה (&, |)

למה false & (1/0 = 0) מתרסק בשגיאת חלוקה באפס, בעוד ש-false and: [1/0 = 0] עובר בשלום?

בדיוק מאותו עיקרון של שליחת הודעות ובלוקים נובע גם ההבדל הקריטי בין שתי משפחות של אופרטורים לוגיים ב-Smalltalk:

⚡ 1. אופרטורים עצלים – הערכה מקוצרת (Short-Circuit: and: ו-or:)

ההודעות and: ו-or: מקבלות בלוק קוד ([...]) כארגומנט, ומעריכות אותו אך ורק במקרה הצורך!
• ב-and:: נשלח value לבלוק אך ורק אם המקבל הוא true. אם המקבל הוא false, המתודה ב-False יודעת מיד שהתוצאה היא שקר ומחזירה false מבלי להריץ את הבלוק!
• ב-or:: אם המקבל הוא true מוחזר מיד true ללא הרצת הבלוק; רק אם המקבל הוא false נשלח value לבלוק.
היתרון: משפר ביצועים ומונע שגיאות ריצה (למשל הגנה מפני חלוקה באפס או פנייה ל-nil בתנאי השני).

⚙️ 2. אופרטורים מלאים – הערכה להוטה (Eager: & ו-|)

האופרטורים הבינאריים & ו-| אינם מקבלים בלוק, אלא מקבלים ערך בוליאני מחושב מראש כארגומנט רגיל!
לפי חוקי השפה הרגילים של Smalltalk, כל ארגומנט של הודעה חייב להיות מחושב במלואו לפני שההודעה עצמה נשלחת אל המקבל.
התוצאה: בביטוי עם & או |, שני הצדדים יוערכו תמיד במלואם — גם אם הצד השמאלי כבר קבע את התוצאה!

שאלה 1 (רמת בסיס): מדוע למופעים של המחלקה Object אין משתני מופע כלל, ומדוע חל איסור מוחלט להוסיף לה משתני מופע? ▼
🎯 הדילמה: לכאורה, היה נוח להוסיף שדה כללי (כגון שם או מזהה) למחלקה Object כך שכל עצם במערכת יירש אותו. מדוע צעד כזה ימוטט את סביבת Squeak?

💡 ההסבר האינטואיטיבי שלי: מכיוון שכמעט כל מחלקה בסביבת Squeak יורשת מ-Object (ישירות או בעקיפין), כל תת-מחלקה יורשת גם את מבנה השדות של מחלקות-העל שלה. לכן, הוספת משתנה מופע ל-Object תשנה מיידית את מבנה הזיכרון הפיזי של כל העצמים במערכת! הדבר יפגע אנושות במחלקות ליבה קריטיות (כגון SmallInteger), אשר המכונה הווירטואלית (VM) מסתמכת על המבנה והייצוג הפיזי המדויק שלהן לצורך ביצועים וניהול זיכרון.

🎯 שורה תחתונה: ל-Object יש 0 משתני מופע וחל איסור מוחלט להוסיף לה שדות, כדי לשמור על מבנה הזיכרון המדויק שה-VM מסתמכת עליו.
שאלה 2 (רמת הבנה): מהו ההבדל בין "התנהגות משותפת" (Common Behavior) לבין "התנהגות ברירת מחדל" (Default Behavior) ב-Object, וכיצד הזוג printString ו-printOn: מדגים זאת? ▼
🎯 הדילמה: מתוך כ-400 מתודות ב-Object, אילו מתודות נועדו לכך שנדרוס אותן בתת-מחלקה שלנו, ואילו מתודות אסור או מיותר לדרוס?

💡 ההסבר האינטואיטיבי שלי:
• התנהגות משותפת (Common Behavior): מתודות גנריות המספקות תשתית שלמה שאין צורך או סיבה לדרוס בתת-מחלקות (למשל printString, ~~, ~=). המתודה printString שולחת לעצם self printStringLimitedTo: 50000, יוצרת זרם תווים (WriteStream), ושולחת לעצם את ההודעה printOn: aStream.
• התנהגות ברירת מחדל (Default Behavior): מתודות בסיסיות שנועדו לכך שתת-מחלקות ידרסו אותן (Overriding) ויספקו מימוש מותאם (למשל printOn: ו-=). ב-Object, מימוש ברירת המחדל של printOn: מדפיס רק 'a ' או 'an ' (לפי title first isVowel) ואת שם המחלקה בעזרת nextPutAll:, ואילו תת-מחלקות כמו Point דורסות את printOn: כדי לכתוב לזרם את הייצוג המדויק x@y.

🎯 שורה תחתונה: אנחנו קוראים ל-printString (התנהגות משותפת), אך דורסים בתת-המחלקות שלנו את printOn: aStream (התנהגות ברירת מחדל).
שאלה 3 (רמת יישום): מדוע במימוש Point >> printOn: aStream מופיעה השורה (y isNumber and: [y negative]) ifTrue: [aStream space], וכיצד זה קשור למושג Self-Evaluating Object? ▼
🎯 הדילמה: למה לנקודה 3 @ 4 לא מוסיפים רווח אחרי @, אבל לנקודה שבה y שלילי מוסיפים רווח ויוצרים 3@ -4?

💡 ההסבר האינטואיטיבי שלי: עצם מסוג Point הוא עצם המשערך את עצמו (Self-Evaluating Object) — כלומר תוצאת ה-printString שלו אמורה להוות קוד Smalltalk תקני שהרצתו מחזירה נקודה בעלת ערך זהה. אם y הוא מספר שלילי (כמו -4), ללא הוספת הרווח היה מודפס הרצף 3@-4. מפענח התחביר של Smalltalk היה מפרש את הרצף @- כהודעה בינארית אחת בלתי מוכרת, ולא כהודעה @ שאחריה המספר השלילי -4! הוספת הרווח באמצעות aStream space יוצרת את המחרוזת '3@ -4', שניתנת לפענוח תחבירי תקין ולקריאה מחדש כנקודה!

🎯 שורה תחתונה: הרווח ב-3@ -4 שומר על כך שהפלט של Point יישאר קוד Smalltalk תקני (Self-Evaluating) גם עבור קואורדינטת y שלילית.
שאלה 4 (רמת ניתוח): הסבר מדוע המערך הדינמי {3@4. 4.5} הוא Self-Evaluating ואילו המערך הדינמי {3@4. 4+5} אינו כזה, וכיצד נדע אם עצם הוא Self-Evaluating בחלון העבודה? ▼
🎯 הדילמה: שני הביטויים יוצרים מערך דינמי תקין בעל שני איברים. מדוע רק הראשון עונה להגדרה של Evaluating Self?

💡 ההסבר האינטואיטיבי שלי: עצם נקרא Evaluating Self כאשר ערכו המודפס (דרך printString או הקשה על ctrl+p בחלון העבודה) זהה לקוד שיצר אותו. מערכים דינמיים ({...}) משערכים את הביטויים שבתוכם בזמן ריצה (מופרדים בנקודה), והם יהיו self-evaluating אך ורק כאשר כל האיברים בתוכם הם בעצמם self-evaluating!
• בביטוי {3@4. 4.5}: גם 3@4 וגם 4.5 משערכים את עצמם, ולכן הדפסת המערך מחזירה {3@4 . 4.5} — זהה לקוד שיצר אותו!
• בביטוי {3@4. 4+5}: הביטוי 4+5 אינו ערך עצמי אלא חישוב שמוערך ל-9, ולכן הדפסתו תחזיר {3@4 . 9} — שאינו זהה לביטוי המקורי {3@4. 4+5}!

🎯 שורה תחתונה: מספרים, תווים, סימבולים, נקודות (Point), תחומים (Interval) ומערכים סטטיים (#(...)) הם Self-Evaluating, ומערך דינמי הוא כזה רק אם כל ביטוייו הם ערכים המשערכים את עצמם.
שאלה 5 (רמת סינתזה): נתח את הקשר המשולש בין ==, = ו-hash: כיצד ממומשת = ב-Object וב-Point, ומדוע דריסת = ללא דריסת hash שוברת מילונים? ▼
🎯 הדילמה: מתכנת יצר מחלקה חדשה, דרס בה את מתודת השוויון = כך שתשווה שדות פנימיים, אך לא דרס את hash. כאשר הוא שמר עצם כמפתח ב-Dictionary וניסה לשלוף אותו בעזרת עצם שווה אחר, המילון החזיר שגיאת KeyNotFound! מדוע?

💡 ההסבר האינטואיטיבי שלי:
1. במחלקה Object, מתודת השוויון = ממומשת כברירת מחדל על ידי בדיקת זהות פיזית: ^self == anObject, ומתודת ה-hash מחזירה מספר שלם המבוסס על זהות העצם בזיכרון.
2. כאשר מחלקה כמו Point דורסת את = לשוויון מבני (בדיקת self species = aPoint species ואז x = aPoint x and: [y = aPoint y]), שני עצמים שונים בזיכרון (p1 == p2 הוא false) נחשבים כעת לשווים לוגית (p1 = p2 הוא true).
3. מילונים (Dictionary) וקבוצות (Set) מאחסנים ומחפשים איברים בטבלת גיבוב לפי התוצאה של hash! אם לא נדרוס את hash, שני עצמים שווים יקבלו מספרי hash שונים (לפי כתובתם בזיכרון), ימופו לתאים (Buckets) שונים במילון, והחיפוש ייכשל לחלוטין!

🎯 שורה תחתונה: חוק בל יעבור ב-OOP: דרסת את =? חובה עליך לדרוס בהתאמה גם את hash כך שלכל a = b יתקיים תמיד a hash = b hash!
🎯 5 שאלות אמריקאיות לאימון עצמי (יחידה 11.1 א'): בחר את התשובה המדויקת ביותר.
1 מדוע חל איסור מוחלט להוסיף משתני מופע למחלקה Object בסביבת Squeak?

המכונה הווירטואלית (VM) מבצעת אופטימיזציות חומרה וזיכרון המניחות שלמחלקת השורש Object יש 0 שדות מופע, ובמיוחד עבור ייצוג ישיר של SmallInteger.
2 כיצד פועל מנגנון ההדפסה של עצמים כאשר שולחים לעצם את ההודעה printString?
📖 הרחבה פדגוגית לשאלה 2▼
שימוש בזרם משותף (WriteStream) מאפשר לעצמים מורכבים (כמו מערך המכיל נקודות) להדפיס את כל איבריהם אל תוך אותו זרם ביעילות באמצעות קריאות רקורסיביות ל-printOn: aStream.

5 מה קובע "חוק הברזל" ב-OOP לגבי דריסת מתודת השוויון = במחלקה חדשה?

מילונים (Dictionary) וקבוצות (Set) מאתרים איברים תחילה לפי hash ורק אז בודקים שוויון עם =. לכן שוויון לפי = מחייב שוויון בערך ה-hash.
💡 5 שאלות עומק מדורגות (יחידה 11.1 ב' – שייכות למחלקה, שכפול, ניפוי שגיאות ואתחול): לחץ על כל שאלה לקריאת ההסבר המלא שלי.
שאלה 1 (רמת בסיס): מה ההבדל בין isMemberOf: לבין isKindOf: על הדוגמה של המספר 4 מול SmallInteger ומול Number, ומדוע מומלץ להימנע מהן בקוד רגיל? ▼
🎯 הדילמה: שתי המתודות בודקות שייכות למחלקה, אך עבור 4 והמחלקה Number האחת מחזירה false והשנייה מחזירה true. מדוע?

💡 ההסבר האינטואיטיבי שלי:
• isMemberOf: aClass בודקת שייכות ישירה ומדויקת בלבד: האם המחלקה הישירה של העצם (self class) היא בדיוק aClass? לכן 4 isMemberOf: SmallInteger מחזיר true, אך 4 isMemberOf: Number מחזיר false!
• isKindOf: aClass בודקת שייכות כולל ירושה: האם העצם הוא מופע של aClass או של כל תת-מחלקה שלה במעלה עץ הירושה? לכן 4 isKindOf: SmallInteger, 4 isKindOf: Number ו-4 isKindOf: Object מחזירים כולם true.
• מדוע זהו Anti-Pattern? בתכנות מונחה עצמים טהור איננו שואלים עצם "מאיזה טיפוס אתה?" או "האם אתה מבין הודעה?" (respondsTo:), משום שזה שובר את הפולימורפיזם ומקשה על הרחבת המערכת. במקום זאת, שולחים את ההודעה לעצם ונותנים למנגנון הקישור הדינמי להפעיל את המתודה המתאימה.

🎯 שורה תחתונה: isMemberOf: = מופע ישיר בלבד; isKindOf: = כולל תת-מחלקות בעץ הירושה; ובעיצוב OOP תקני נמנעים משתיהן וסומכים על פולימורפיזם!
שאלה 2 (רמת הבנה ויישום): הסבר מה קורה בזיכרון בקטע הקוד a1 := {{'a'. 'b'}. {'c'. 'd'}}. a2 := a1 shallowCopy. (a1 at: 1) at: 1 put: 'z', ומה ישתנה אם נחליף ל-copyTwoLevel או ל-deepCopy? ▼
🎯 הדילמה: ביצענו השמה רק על a1, אך כשבדקנו את a2 גילינו שגם בו האיבר הראשון השתנה ל-'z'! כיצד זה קרה?

💡 ההסבר האינטואיטיבי שלי: משתני מופע ואיברי מערך ב-Smalltalk ממומשים כמצביעים לזיכרון (Pointers).
• ב-shallowCopy (שכפול רדוד): משוכפל רק מערך השורש החיצוני, אך שני האיברים שבתוכו (תתי-המערכים {'a'. 'b'} ו-{'c'. 'd'}) מועתקים כמצביעים זהותיים ומשותפים בין a1 ל-a2! לכן שינוי בתוך תת-המערך הראשון דרך a1 משתקף מיד גם ב-a2.
• ב-copyTwoLevel: משוכפל השורש ומשוכפל רדודה גם כל אחד מאיברי הרמה הראשונה, ולכן במערך דו-ממדי זה a2 לא ייפגע מהשינוי ב-a1. אולם במערך תלת-ממדי ({{{'a'}. {'b'}}. {{'c'}. {'d'}}}), הרמה השלישית תישאר משותפת!
• ב-deepCopy (שכפול עמוק): מתבצע שכפול רקורסיבי מלא של כל גרף העצמים בכל רמות העומק.

🎯 שורה תחתונה: שכפול רדוד יוצר שורש חדש שחולק את אותם עצמים פנימיים עם המקור.

🔑 מעבדת זהות (==), שוויון (=) וחוזה ה-hash (סעיף 11.1)

במחלקה Object, מתודת השוויון = ממומשת כברירת מחדל של זהות (^self == anObject). כאשר דורסים את = (למשל במחלקה Point הבודקת species ואז משווה את x ו-y), חובה לדרוס בהתאמה גם את hash כך ששני עצמים שווים יחזירו תמיד את אותו ערך hash מדויק לצורך אחסון וחיפוש במילונים!

🖥️ מעבדת השכפול בזיכרון ה-RAM (סעיף 11.1)

מכיוון שמשתני מופע ב-Smalltalk הם מצביעים לזיכרון, shallowCopy משכפלת רק את השורש ומשתפת את תתי-המערכים; copyTwoLevel משכפלת שתי רמות (אך משתפת ברמה השלישית); deepCopy משכפלת רקורסיבית את כל הגרף; והגישה התקנית היא copy הקוראת ל-self shallowCopy postCopy.

🧮 מעבדת המספרים והחילוק ב-Smalltalk (סעיף 11.2)

ב-Smalltalk מספרים הם עצמים מלאים היורשים מ-Magnitude ומ-Number. חילוק / יוצר שבר מצומצם מדויק Fraction, חילוק שלמים // מעגל כלפי מטה, שארית \\ מחושבת כ-self - (self // aNumber * aNumber), וחריגה מ-SmallInteger מומרת אוטומטית ל-LargePositiveInteger או ל-LargeNegativeInteger.

💎 מעבדת ByteString מול Symbol (סעיפים 11.3–11.4)

מחרוזת רגילה (ByteString, נכתבת 'hello') אינה ייחודית בזיכרון (== מחזיר false) וניתנת לשינוי באמצעות at:put:. לעומתה, סימבול (Symbol, נכתב #hello) הוא עצם ייחודי במערכת (Interned, ולכן == מחזיר תמיד true) ובלתי ניתן לשינוי (Immutable).

⚡ מעבדת ה-Short-Circuit והפולימורפיזם הבוליאני (סעיף 11.5)

המחלקות True ו-False (והמופעים היחידים true ו-false) מממשות תנאים פולימורפית ללא משפט if. האופרטורים העצלים and: ו-or: מקבלים בלוק ומעריכים אותו רק בעת הצורך, בעוד שהאופרטורים המלאים & ו-| מעריכים תמיד את שני הצדדים מראש.
